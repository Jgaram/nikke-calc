# 단계 0P·R — 프리뷰 전사와 출시 후 정식 등록


> char-add 워크플로우의 절차 문서. 진입점·게이트 규칙은 `SKILL.md`.

신캐는 출시 1~3일 전에 **스킬 레벨 10 기준 카드 이미지**로 스킬이 먼저 공개된다.
블라링크(스크래퍼 소스)는 인게임 업데이트 후에야 갱신되므로, 그 사이 등록하려면
카드 원문을 손으로 옮겨 적는 수밖에 없다.

이 문서는 그 선행 등록(단계 0P)과, 출시 후 스크랩 원문과 대조해 정본으로 승격하는
정식 등록(단계 R)을 다룬다. 두 단계 사이의 1~3은 일반 캐릭터와 완전히 같다 —
`preview_skills.json`이 `nikke_scraped.json`과 같은 스키마이기 때문이다.

---

## 판정 규칙

- **등록 여부** = `data/parsed_skills.json`에 키가 있는가
- **정본 여부** = `scraper/preview_skills.json`에 키가 **없는**가

**이름에는 프리뷰임을 표시하지 않는다.** 키는 카드에 적힌 정식 명칭 그대로 쓴다 —
프리뷰 여부는 어느 파일에 있는가로만 판정하므로 이름에 표식을 붙이면 출시 후 대조만 어려워진다.
(`(가칭)`이 붙은 이름이 실제로 있지만 그건 정식 이름의 일부다 — `context/ALIASES.md` §주의.)

프리뷰 캐릭터는 "등록됐지만 정본이 아닌" 상태다. `--check`가 신규로 보고하면서
동시에 파싱이 이미 있는 유일한 케이스이므로, 신규도 변경도 아닌 **정식 등록 대상**으로 다룬다.

---

## 단계 0P — 전사

### Step 0. 전사할 이유가 있는지 확인 (필수)

프리뷰는 **출시 전이라 스크래퍼로 못 가져오는 동안만** 의미가 있다. 시작 전에 확인한다:

```bash
python -c "import json,sys; sys.stdout.reconfigure(encoding='utf-8'); \
n=json.load(open('scraper/nikke_scraped.json',encoding='utf-8')); \
s=json.load(open('data/parsed_skills.json',encoding='utf-8')); \
name='<캐릭터명>'; print('스크랩', name in n, '/ 파싱', name in s)"
```

- **스크랩 있음** → 이미 출시됐다. 프리뷰로 옮겨 적을 이유가 없다.
  카드가 아니라 정식 데이터로 간다 — 파싱 없으면 단계 1, 있으면 그냥 등록 완료다. **여기서 멈춘다.**
- **스크랩 없음 · 파싱 있음** → 이미 프리뷰로 등록된 상태다. 단계 1~4 중 어디까지 갔는지 보고 이어간다.
- **둘 다 없음** → 아래 Step 1로 진행.

이름이 닮은 다른 캐릭터를 착각한 것일 수도 있으므로, 스크랩에 있으면 그 이름을 유저에게 보여주고 확인받는다.

### Step 1. 이미지 보관

카드 이미지를 `image/preview/`에 저장한다. 파일명은 캐릭터명 기준, 콜론 `:` → `_` 치환.
스킬이 여러 장으로 나뉘어 공개되므로 전부 받는다(스킬1 / 스킬2·버스트가 흔한 분할).

### Step 2. 원문 전사

`scraper/preview_skills.json`에 항목을 만든다. **요약·정규화 없이 그대로** 옮긴다 —
`■` clause 구분, 대괄호 블록, 줄바꿈을 원문대로 유지한다.
출시 후 diff가 이 충실도에 전적으로 의존하므로, 표현을 다듬으면 그만큼 대조가 무력해진다.

수치는 `template`의 `{0}`·`{1}` 자리로 빼고 `values`의 `"10"` 키에 순서대로 넣는다.
`values`에 레벨 1~9를 만들지 않는다 — 카드에 없는 값을 보간하면 추정치가 정본 파일에 섞인다.

```json
"<캐릭터명>": {
  "_preview": {
    "공개일": "YYYY-MM-DD",
    "출처": ["image/preview/<파일>.png"],
    "미확정": ["스쿼드 코드(카드에 없음)", "post_fire_delay 실측", "..."]
  },
  "레어도": "SSR", "클래스": "화력형", "기업": "미상", "속성": "풍압", "버스트 단계": "3",
  "무기상세": {
    "무기유형": "RL", "최대 장탄 수": "120", "재장전 시간": "2.50s",
    "무기스킬": "■ 대상에게\n[공격력 2.5% 대미지]\n[차지 시간 : 1초]\n..."
  },
  "스킬": {
    "<스킬명>": { "쿨타임": "40.0 s", "template": "■ ...", "values": { "10": ["..."] } }
  }
}
```

카드 우상단 무기 블록이 `parse_nikke.py`가 쓰는 값을 거의 다 준다 —
무기유형·최대 장탄 수·재장전 시간·`damage_coeff`(= "공격력 N% 대미지")·`core_dmg_mult`·
`charge_time`·`full_charge_mult`. 클래스·버스트 단계·코드(속성)는 카드 상단에 있다.

### Step 3. 미확정 목록

카드에서 읽을 수 없는 항목을 `_preview.미확정`에 나열한다. **추측해서 채우지 않는다** —
빈 채로 둬야 출시 후 무엇을 확인할지가 남는다.

카드로 확정할 수 없는 것(출발점 목록. 이 캐릭터에만 해당하는 것을 추가한다):
스킬 레벨 1~9 계수, 기업·스쿼드, RL/SR의 `post_fire_delay`·`post_reload_delay` 실측,
무기 변경 무기의 연사속도, 카운터의 기준(발사 단위 vs 탄환 단위), 스택 갱신/초기화 규칙,
동일 timing 내 실행 순서. 스쿼드 조건부 효과가 있으면 그 효과는 검증 불가로 표시한다.

**단계 0P 시작 시 이 한계를 유저에게 고지한다.** 목록은 시나리오 `## 프리뷰 미확정`에도
그대로 옮겨 적고, 단계 R Step 5의 검증 항목이 된다.

### Step 4. 전사 확인

전사한 항목을 **통째로** 유저에게 보여주고 오독을 확인받는다. 이미지 판독 오류는
이후 모든 단계를 오염시키므로 여기서 잡아야 한다. 확인 후 단계 1(시나리오 초안)로 넘어간다.

### Step 5. 현황 등록

`context/PARSING-CHARS.md` 현황 목록 `### 프리뷰`에 이름을 넣는다.
파싱이 끝나도 `### 완료`로 옮기지 않는다 — 정식 등록 전에는 완료가 아니다.

## 단계 R — 출시 후 정식 등록

`doclint.py` 검사 G가 "출시됨 — 정식 등록 필요"로 실패시키면 이 단계다.

### Step 1. 수집

```bash
python scraper/cdn_fetch.py --check   # 무엇이 신규로 잡히는지 확인
python scraper/cdn_fetch.py           # 반영
```

### Step 2. 이름 대조

카드에서 읽은 표기가 CDN 키와 다를 수 있다(콜론 앞뒤 공백, 부제 추가·변경).
다르면 유저 확인 후 `context/ALIASES.md` · 시나리오 파일명 · `parsed_skills.json` 키 ·
`preview_skills.json` 키를 **함께** 옮긴 뒤 진행한다.

이름이 닮았다고 같은 캐릭터로 단정하지 않는다 — `레이`와 `레이 (가칭)`처럼 **별개 캐릭터**인
경우가 있고, `(가칭)`은 정식 이름의 일부다(`ALIASES.md` §주의). 판단은 유저가 한다.

### Step 3. 원문 diff

```bash
python -m scraper.preview_diff <이름>
```

프리뷰 원문 ↔ 스크랩 원문을 공백·태그 정규화 후 스킬별로 대조하고, `values["10"]`도 비교한다.

### Step 4. 판정

- **일치** — `preview_skills.json`에서 항목을 제거하고, `parsed_skills.json`의 해당 캐릭터
  `values`에 레벨 1~9를 채운다. `python -m context.snapshot`으로 회귀.
  **총딜이 변하면 레벨 10 값이 실제로 달랐다는 뜻이므로 멈추고 보고한다.**
- **불일치** — diff를 **그대로** 유저에게 제시하고 단계 2(파싱)부터 재검토한다.
  사소해 보이는 문구 차이도 에이전트가 "영향 없음"으로 판정하지 않는다
  (`../char-scrape/SCRAPER.md`의 등록 캐릭터 변경 규칙과 동일).

### Step 5. 미확정 항목 검증

`_preview.미확정`을 인게임으로 하나씩 확인해 시나리오 `## 해석 선언`과
`## 프리뷰 미확정` 표를 갱신한다. RL/SR이면 `post_fire_delay`·`post_reload_delay` 실측값을
유저에게 묻고, 기본값과 다를 때만 `data/weapon_delays.json`의 `_exceptions`에 기록한다.

### Step 6. 흔적 제거 (필수)

정식 등록이 끝나면 **프리뷰였다는 사실은 어디에도 남지 않는다.** 남은 표기는 다음 세션이
검증 끝난 캐릭터를 미검증으로 읽게 만드는 오염원이다. 다음을 전부 지운다:

| 대상 | 처리 |
|---|---|
| `scraper/preview_skills.json` 항목 | 삭제 (Step 4) |
| `context/PARSING-CHARS.md` | 이름을 `### 프리뷰` → `### 완료`로 이동 |
| 시나리오 모드 표기 | `보강 (프리뷰)` → `보강` |
| 시나리오 `## 프리뷰 미확정` 절 | **절 통째로 삭제.** 검증으로 확정된 해석은 `## 해석 선언`에, |
| | 유저가 답한 것은 `## 유저 확인 사항`에 옮겨 적은 뒤 지운다 |
| `image/preview/<캐릭터>*` | 삭제 (정식 이미지는 `image/`에 따로 수집된다) |
| `data/parsed_nikke.json`의 `preview: true` | 자동 소멸 — 스크랩 항목이 이긴다. 재실행만 하면 된다 |

`python -m context.doclint`가 통과하면 정식 등록 완료다 — 검사 G가 위 흔적을 잡는다.

---

## Gate

단계 0P 종료 시, 단계 R의 각 Step 종료 시 모두 유저에게 보고하고 다음 진행 여부를 묻는다
(`SKILL.md` 단계 게이트). 특히 Step 4의 불일치 판정은 자체 판단으로 넘어가지 않는다.
