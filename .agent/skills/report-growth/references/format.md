한 캐릭터의 육성 변수를 **정한 덱 안에서 한 축씩** 움직여, 덱 전체 딜과 그 캐릭터
자신의 딜이 각각 얼마나 오르는지 재는 도구.

```bash
python .agent/skills/report-growth/scripts/growth.py .report-work/<이름>/spec.json
python .agent/skills/report-growth/scripts/growth.py <스펙> --runs 12 --jobs 8 --open
python .agent/skills/report-growth/scripts/growth.py <스펙> --dry-run
python .agent/skills/report-growth/scripts/growth.py <스펙> --from-cache
```

- 입력: `.report-work/<스펙명>/spec.json` (덱 + 기준 육성 + 축 목록)
- 출력: `reports/<스펙명>.html`
- 캐시: `.report-work/<스펙명>/result.data.json`

스쿼드 보고서(`.agent/skills/report-squad/references/format.md`)와 러너·기본 스펙·이미지·운용 조건 블록을
공유한다. 다른 것은 셋뿐이다.

| | 딜량 보고서 | 육성 효율 보고서 |
|---|---|---|
| 케이스 | 손으로 쓴 비교군 | 덱 × 축 × 단계로 **자동 전개** |
| 비교 | 케이스별 평균끼리 | **페어드 델타** (시드별 차의 평균) |
| 지표 | 덱 총딜 | 덱 총딜 Δ + **대상 캐릭터 자신의 딜 Δ** |

---

## 왜 페어드 델타인가

스킬 1레벨은 보통 덱 총딜 0.5~1.5%인데, 시드 간 CV도 0.5~1.5%다. 케이스별 평균을 빼면
차이가 난수에 묻혀 부호조차 안 정해진다. 모든 케이스가 **같은 시드셋 `1..runs`** 를 쓰므로,
시드별로 먼저 기준과의 차를 구하고 그 평균을 내면 난수 성분이 대부분 상쇄된다.

보고서의 `±`는 그 차이의 **2·표준오차**다. `|Δ| ≤ 2SE`면 `판정 불가`로 적고 중립색으로
칠한다 — 이 회차 수로는 방향조차 말할 수 없다는 뜻이며, 회차를 늘리면 `±`가 √n에
반비례해 줄어든다.

**랜덤 시드는 제공하지 않는다.** 짝지어 빼는 것이 이 보고서의 전부라서다.

## 모드 — 스킬과 옵션을 섞지 않는다

`mode`는 기준 육성과 축을 자동으로 만든다. **한 보고서는 한 종류만 조사한다** — 옵션 효율은
스킬이 만렙일 때의 값이고 스킬 효율은 옵션이 기본값일 때의 값이라, 섞으면 어느 쪽 Δ도
"지금 내 계정에서의 값"이 아니게 된다.

| `mode` | 고정 | 축 | 케이스 |
|---|---|---|---|
| `"skill"` | 장비 옵션 = **기본 스펙 그대로** | 1스킬·2스킬·버스트 레벨, 기준 7 + 8·9·10 | 10개 |
| `"option"` | 스킬 = **10/10/10** | 공격력·최대장탄·크리확률·크리대미지, 각 **0~4줄** | 17개 |
| (없음) | — | 스펙의 `axes`만 (모드 이전 스펙이 그대로 돈다) | — |

옵션 모드의 기준은 **우월코드 4줄만 붙고 나머지 옵션은 0**인 상태다. 거기서 각 옵션을
줄 단위로 올린다. 줄 수치는 전부 **레벨 10**이며 `spec.overload()`가
`data/base_stat_tables/equipment_skills.json`에서 유도한다 — 손으로 적지 않는다.

| 옵션 | 1줄 | 2줄 | 3줄 | 4줄 |
|---|---|---|---|---|
| 공격력 | 11.11% | 22.22% | 33.33% | 44.44% |
| 최대장탄 | 64.82% | 129.64% | 194.46% | 259.28% |
| 크리티컬 확률 | 5.37% | 10.74% | 16.11% | 21.48% |
| 크리티컬 대미지 | 15.46% | 30.92% | 46.38% | 61.84% |
| 차지속도 | 4.63% | 9.26% | 13.89% | 18.52% |
| 차지대미지 | 11.11% | 22.22% | 33.33% | 44.44% |
| 우월코드 | 22.15% | 44.30% | 66.45% | 88.60% |

추가 축은 두 가지 조건으로 붙는다.

- **차지속도·차지대미지** — 대상 무기가 `RL`·`SR`이면 자동. 다른 무기군에 강제로 넣으려면
  `"charge_axes": true` (효과가 없어 전부 0으로 나온다).
- **우월코드** — `"include_element_bonus": true`일 때만. **기준이 4줄**이라 0~3줄이 음수 Δ로
  나온다 ("4줄을 안 맞추면 이만큼 잃는다"). 다른 축과 기준을 공유해야 나란히 비교할 수
  있어서 이렇게 잡는다. 대상이 랩쳐 약점 속성이 아니면 전부 0이며, 그때는 실행 시
  경고가 나온다.

## 재화 효율 — 스킬 모드에만 붙는다

`mode: "skill"`이면 Δ 옆에 **메뉴얼 비용**이 함께 나온다. 옵션 모드에는 붙지 않는다
(오버로드는 재화 비용이 확률 시행이라 장수로 환산할 수 없다).

| | 먹는 재화 | 7→8 | 8→9 | 9→10 | 7→10 |
|---|---|---|---|---|---|
| 1스킬·2스킬 | 스킬 메뉴얼 | 90 | 105 | 120 | 315 |
| 버스트(3스킬) | 버스트 메뉴얼 | 90 | 105 | 120 | 315 |

이 표는 사본이다. 정본은 `growth.py`의 `MANUAL_COST`·`MANUAL_KIND`다.

- **7레벨까지는 무료로 본다.** 사실상 수급 제한이 없어 순서를 정할 때 변수가 아니다.
  전부 만렙이면 스킬 메뉴얼 630장 + 버스트 메뉴얼 315장이다.
- **장수를 한 단위로 환산하지 않는다.** 두 메뉴얼은 서로 대체되지 않으므로 각자의 실제
  장수로 적는다. 스킬 메뉴얼이 버스트 메뉴얼보다 두 배 들어온다는 사실은 **보고서에 적지
  않는다** — 계정마다 다른 사정이라 숫자로 굳히지 않는다. 종류가 다른 줄을 나란히 옮길 때
  사람이 덧붙인다 (`SKILL.md` Step 5). 축이 곧 메뉴얼 종류라 표에서 경계는 보인다.
- 효율의 단위는 **100장당 덱 딜 Δ(%p)** 다. 1장당으로 적으면 소수점 넷째 자리가 된다.
- 줄은 **스킬창과 같은 순서**(1스킬 → 2스킬 → 버스트, 레벨 오름차순)로 둔다. 효율순으로
  재정렬하지 않는다 — 찾으려던 칸이 매번 다른 자리에 있으면 오히려 읽기 어렵다.
  순위는 `100장당` 열의 미니 막대로 읽는다.
- **순서를 추천하지 않는다.** 어느 칸이 얼마짜리인지까지만 낸다 — 남은 메뉴얼과 목표는
  보고서가 알 수 없다. 두 칸을 같이 올렸을 때가 궁금하면 `combos`로 실측한다.
- 비용표는 `"cost": {"level_cost": {...}, "kind": {...}}`로 덮고,
  `"cost": {"enabled": false}`로 끈다.

한 칸의 증분 Δ도 **페어드로** 잰다(직전 단계 케이스 대비). 그래야 그 증분이 노이즈보다
큰지 말할 수 있고, `판정 불가`인 칸은 표에 그렇게 적힌다.

---

`option_lines`(기본 `[0,1,2,3,4]`)·`skill_steps`(기본 `[7,8,9,10]`)로 단계를 바꿀 수 있다.
`baseline`·`axes`를 스펙에 직접 적으면 자동 생성분 **위에 얹히고 뒤에 붙는다** — 모드는
출발점이지 잠금이 아니다.

## 스펙 형식

```jsonc
{
  "title": "보고서 제목",
  "note": "부제 — 무엇을 조사하는지 한 줄",
  "subject": "브리드 : 사일런트 트랙",   // 조사 대상. 모든 덱에 들어 있어야 한다
  "mode": "option",                     // "skill" | "option" | 없음
  "runs": 10,
  "cost": { "enabled": true },          // 선택 — 메뉴얼 비용 모델. 스킬 모드에만 쓰인다

  "defaults": { /* 전 케이스 공통 육성 오버라이드 */ },
  "config":   { /* 전 케이스 공통 시뮬 설정 */ },
  "enemy":    { /* 전 케이스 공통 랩쳐 설정 */ },

  "decks": [                            // 1~3개. 보고서에서 탭이 된다
    { "name": "덱 이름", "squad": ["정식 명칭", "..."],
      "note": "", "defaults": {}, "config": {}, "enemy": {}, "no_layer": false }
  ],

  "baseline": {                         // 대상의 **기준 육성**. Δ는 여기서 잰다
    "collection_stage": "SR0"           // `mode`가 만든 기준 위에 얹힌다
  },

  "axes": [                             // 모드 축 **뒤에** 붙는다. 축마다 하나씩만 움직인다
    { "name": "버스트 레벨",
      "note": "선택 — 축 설명",
      "target": "다른 캐릭터",           // 선택. 없으면 subject
      "steps": [
        { "label": "7", "base": true },                              // 기준 단계 (정확히 1개)
        { "label": "10", "over": { "skill_levels": { "3": 10 } } }   // baseline 위에 얹는다
      ] }
  ],

  "combos": [                           // 선택 — 두 단계를 같이 올렸을 때
    { "label": "버스트 10 + 공격력 2줄",
      "of": ["버스트 레벨:10", "공격력 옵션:2줄 (22.22%)"] }   // `축이름:단계라벨`
  ]
}
```

육성 필드·시뮬 설정·랩쳐 설정의 키와 기본값은 전부 딜량 보고서와 같다 —
`.agent/skills/report-squad/references/format.md §육성 필드`·`§시뮬 설정`·`§랩쳐 설정`이 정본이다.
`defaults`·`config`·`enemy`·`no_layer`는 전역 → 덱 순으로 겹친다.

### baseline과 over

`baseline`은 **대상 캐릭터에게만** 얹힌다. 스쿼드 전원을 낮춰 잡으려면 `defaults`를 쓴다.

`over`는 `baseline` 위에 재귀 병합된다. 그래서 `equip_skills`의 다른 옵션(우월코드 88.6% 등)은
그대로 남고 적은 키만 바뀐다. 기준 단계에는 `over`를 적지 않는다 — 기준 육성의 정본은
`baseline` 하나여야 한다.

**축은 반드시 한 번에 하나만 움직인다.** 두 개를 같이 보고 싶으면 `combos`를 쓴다.
그래야 실측값과 "각각 따로 올린 Δ의 단순 합"을 비교해 상호작용을 잴 수 있다.

### 시뮬 횟수

케이스 = `덱 × (비-기준 단계 수 + 조합 수 + 1)`. 기준 단계는 **덱당 한 번만** 돌려 전 축이
공유하고, 육성 dict가 같아진 단계끼리도 한 케이스로 합쳐진다.

`mode: "skill"` 10개(100회 ≈ 7분) · `mode: "option"` 17개(170회 ≈ 12분) · 차지형이면
25개(250회 ≈ 18분)가 기준이다. 덱을 늘리면 그만큼 곱해진다.
**스펙을 짜면 먼저 `--dry-run`으로 횟수를 확인한다.**

## 보고서 구성

| 섹션 | 내용 |
|---|---|
| 조사 범위 | 최상단. `mode`가 무엇을 고정하고 무엇을 움직였는지 — 이 줄이 없으면 Δ가 무엇 대비인지 알 수 없다 |
| 탭 | 덱마다 하나. 덱이 하나면 탭이 없다 |
| 랩쳐 · 운용 조건 | 딜량 보고서와 같은 블록. **기준 케이스만** 넣어 만든다 — 축이 바꾸는 값은 여기 섞지 않는다 |
| 기준 | 스쿼드 이미지 · 기준 덱 총딜(CV) · 대상 본인 딜과 덱 내 비중 · 풀버스트 횟수 |
| **재화 효율** | `mode: "skill"`에만. 한 칸당 메뉴얼 장수와 100장당 덱 딜 Δ. 축 순서 그대로 |
| **축별 상세** | 본체. 축마다 단계별 발산 막대 2열(덱 딜 Δ / 본인 딜 Δ) + 직전 단계 대비 증분 |
| 조합 검증 | `combos`가 있을 때. 실측 Δ vs 단순 합, 그 차이 |
| 덱 간 대조 | 덱이 2개 이상일 때. 같은 투자의 덱별 덱 딜 Δ |
| 원자료 | 회차별 총딜, 기준 육성 오버라이드 |

### 색과 막대

- Δ는 부호가 뜻을 가지므로 **발산형**이다 — 0을 가운데 두고 증가/감소가 다른 색,
  `판정 불가`는 중립 회색. 색만으로 뜻을 전하지 않도록 숫자와 라벨을 언제나 같이 적는다.
- **덱 딜과 본인 딜은 한 막대에 섞지 않는다.** 두 열로 나란히 놓고 **열마다 배율을 따로**
  잡는다 (버퍼는 본인 딜 Δ가 두 자릿수인데 덱 딜 Δ는 1% 안팎이라, 한 배율로 묶으면
  정작 중요한 덱 딜 막대가 실처럼 얇아진다). 두 배율은 범례에 수치로 적는다.
- 색 토큰은 딜량 보고서(`report_html._CSS`)를 그대로 쓴다. 라이트/다크 검증본이다.

## 주의

- **Δ는 이 덱 · 이 랩쳐 · 이 기준 육성에서의 값이다.** 덱이 바뀌면 순위가 바뀌는 게
  이 보고서를 만드는 이유다 — 다른 덱에 그대로 옮기지 않는다.
- 버퍼는 **본인 딜 Δ가 0이어도 덱 딜 Δ가 크다.** 두 열을 같이 읽어야 한다.
- 랩쳐 코드를 비우면 전원 속성 특효가 꺼져 Δ 순위까지 흔들린다. 반드시 지정한다.
- 총딜 절대값은 스펙 고정 비교값이며 실전 기대딜이 아니다.
- 재화 효율은 **스킬·버스트 메뉴얼뿐이다.** 오버로드·소장품·돌파 재화는 다루지 않는다.
