# 회귀 하네스

계산기를 고친 뒤 **기존 캐릭터가 조용히 틀어졌는지** 잡는 도구.

```bash
python -m runner.snapshot                  # 전체 비교
python -m runner.snapshot --squad S40_브리드라피   # 일부만
python -m runner.snapshot --list           # 스쿼드 목록
python -m runner.snapshot --update         # baseline 갱신 (유저 확인 후에만)
python -m runner.snapshot --jobs 1         # 순차 실행 (디버깅용)
```

스쿼드 단위로 병렬 실행한다 (기본 = CPU 수·최대 8). `--jobs 1`이면 네 배쯤 느리지만
**결과는 어느 쪽이든 같다.** FAIL 시 exit code 1.

## 기본 스펙 — `runner/spec.py`

총딜 수치를 해석하려면 어떤 스펙으로 돌린 것인지 알아야 한다. 스쿼드 dict는 이름만 주고
나머지는 `runner/spec.py`가 채운다. **하네스 전용이 아니다** — `runner/sim.py`도,
이 레포를 읽어 보고서를 내는 별도 웹앱 레포도 같은 것을 쓴다. 여러 도구의
총딜을 서로 견줄 수 있는 건 기본 스펙이 하나이기 때문이다.

합성은 세 층이고, 그 사이에 선택 레이어가 하나 낀다 (뒤가 이긴다, dict는 재귀 병합):

```
spec.DEFAULT_CHAR → data/char_defaults.json[이름] → 육성 프로필(선택) → 호출자 오버라이드
   기본 육성 스펙      캐릭터별 기본 레이어            내 계정 실제 육성      스쿼드/케이스별 예외
```

#### 풀버스트 상한 — `_max_burst_count`

**시뮬 자체는 상한이 없다** (`timeline` 기본 `None`). 상한을 거는 건 보고서 러너뿐이고
(기본 14회), 사이클이 빠른 스쿼드는 거기 걸려 **조용히 낮게 나온다.** 그래서 필요한 값을
캐릭터 레이어에 등록해 두고 스쿼드에 그 캐릭터가 있으면 러너가 올린다
(`spec.max_burst_floor()` — 이 레포가 내주는 하한을 보고서 러너가 읽는다).

`999` 같은 값을 스펙에 박는 것과 다르다 — 상한이 왜 필요한지가 캐릭터에 붙어 있고,
같은 캐릭터를 쓰는 다른 보고서에도 따라간다. **스펙에 `max_burst_count`를 적으면 그 값이
이긴다** (일부러 낮춰 자르는 것도 유효한 비교다).

**`timeline.py`는 이 파일을 읽지 않는다.** `simulate()`는 넘겨받은 캐릭터 dict만 본다 —
기본값이 시뮬 결과를 소리 없이 바꾸면 안 되기 때문이다. 레이어를 얹는 건 언제나 러너 쪽이다.

#### 버스트 운용 패턴

캐릭터마다 "몇 번째 풀버스트에 버스트를 쓰는가"가 정해져 있는 경우가 있다. 카탈로그를
`_burst_patterns`에 이름 붙여 저장하고, **어느 조합에서 어느 패턴을 쓸지는 `_rules`**로 적는다
(조건부 컨트롤과 같은 스키마다 — `CONTROL.md §부착`).

**패턴은 컨트롤이다** — 버스트도 유저가 아이콘·`a`·`s`·`d`로 직접 누르는 다섯째 버튼이라
(`CONTROL.md §L0`), 규칙의 `apply`에서 `control["burst"]["pattern"]` 자리에 산다.

```jsonc
"마스트 : 로망틱 메이드": {
  "_burst_patterns": { "3의 배수": "every:3", "1,3,5,9,11,14": [1, 3, 5, 9, 11, 14] },
  "_rules": [                       // 조건이 맞는 규칙 전부를 순서대로, 뒤가 이긴다
    { "when": { "same_stage_cd_max": 20 },
      "apply": { "control": { "burst": { "pattern": "3의 배수" } } } },
    { "when": { "same_stage_cd_max": 20, "position": 1 },   // 좁은 조건을 아래에
      "apply": { "control": { "burst": { "pattern": "1,3,5,9,11,14" } } } }
  ]
}
```

아무 규칙도 안 맞으면 **패턴이 아예 없다** — 그 조합에서는 평소 순서(왼쪽부터)가 맞다.

양 끝 값의 뜻 — `"every:1"`은 **매 사이클 등급 0**(그 단계를 전담한다. 미란다·츠바이·토브),
빈 목록 `[]`은 **어느 사이클도 차례가 아니다** = 늘 등급 2다. 후자는 패턴 없음(등급 1)과
다르므로 `_pattern_rank`는 falsy가 아니라 `is None`으로 가른다.

**패턴은 후보에서 빼는 게 아니라 순서를 바꾼다** (`timeline._pattern_rank`).

| 등급 | 누구 | 효과 |
|---|---|---|
| 0 | 패턴이 있고 **이번 사이클이 그 차례** | 패턴 없는 동료보다 **앞선다** |
| 1 | 패턴 없음 | 평소 순서 |
| 2 | 패턴이 있으나 이번 차례가 아님 | 맨 뒤 — 앞사람이 전부 쿨이면 그래도 나간다 |

등급 2가 있어서 단계가 **막히지는 않는다** — 앞사람이 전부 쿨이면 차례가 아니어도 나간다.

**적용 조건 — `_rules[].when`**

"정석"이 조합에 달린 경우가 있다. 마스트 : 로망틱 메이드의 3의 배수는 **20초 쿨 2버와
함께일 때** 성립하는 운용이고, 같은 단계가 40초짜리뿐이면(앵커 : 이노센트 메이드와 둘 등)
격 사이클로 번갈아 쓰는 평소 순서가 맞다. 조건이 안 맞으면 패턴을 **아예 걸지 않는다.**
같은 조건 안에서 정석이 또 갈리면 **좁은 조건을 아래에** 적어 뒤가 이기게 한다 — 마스트가
유일한 사용처로, 20초 쿨 2버와 함께라는 조건 아래 가장 왼쪽이면 `1,3,5,9,11,14`,
아니면 `3의 배수`다.

조건 어휘는 조건부 컨트롤과 **완전히 같다**(`spec.WHEN_KEYS`). 정본은 `CONTROL.md §부착`.

| 조건 키 | 의미 |
|---|---|
| `same_stage_cd_max: N` | 같은 버스트 단계에 쿨타임 N초 이하인 **다른 멤버가 있을 때만** 적용 (`burst_stage: "A"`는 어느 단계로도 센다) |
| `same_stage_other: true` | 같은 단계에 **다른 멤버가 하나라도 있을 때만.** 자기가 그 단계의 유일한 멤버면 패턴("안 씀")이 무의미하므로 떼어낸다 |
| `with_member: [이름...]` | 목록 중 **하나라도 스쿼드에 있을 때만** (프리카 ← 민트) |
| `position: N` | 스쿼드 배치가 **N번째일 때만** (1 = 가장 왼쪽) |
| `equip_skill_min: {옵션: 하한}` | 그 장비 옵션의 **합산 퍼센트**가 하한 이상일 때만 (앨리스 차지속도 가드) |
| `atk_rank: {top: N, exclude: [...]}` | `exclude`를 뺀 스쿼드에서 **정적 공격력 N위 안**일 때만. 동률은 안에 들지 않는다 (미하라 공격력 가드) |

규칙은 **레이어 기본값에만** 걸린다. `chars`·보고서 스펙·CLI로 직접 지정한 패턴은 조건을
보지 않는다 — 지정은 언제나 이긴다(값이 우연히 기본값과 같아도 그렇다. 규칙을 얹은 뒤
호출자 오버라이드를 다시 얹는 구조라서다). 판정은 `spec.resolve_rules()`가 **스쿼드를 다
조립한 뒤** 하고, **조건에 안 걸린 패턴은 캐릭터 dict에 아예 안 들어가므로 이탈 보고에도
실제로 걸린 것만 남는다.**

바꾸는 법: `chars`/보고서 스펙에 `"burst_pattern": "1,3,5,9,11,14"`, 끄려면 `null`
(CLI는 `--burst-pattern "이름:패턴"` / `"이름:없음"`). 등록되지 않은 이름을 주면 즉시 에러다.
**이 최상위 `burst_pattern` 키는 「지정」 자리이고 레이어를 이긴다** — 키가 있으면 값이
`null`이어도 그쪽이 쓰인다(그래야 끄는 게 된다).

**사이클 안에서 늦게 누르는 것**(딜레이 버스트)은 `control["burst"]["delay"]`다
(CLI `--burst-delay "이름:초"`). 기본 0이라 안 주면 종전과 같고, 주면 그 단계 전체가
밀린다 — `CONTROL.md §딜레이 버스트`.

`burst_sequence`(사이클별 명시 순서)를 준 config에서는 패턴이 무시된다 — 그쪽이 전부 결정한다.

#### 카메라 · 조작 모드 · 택틱은 스쿼드 스펙의 일부다

`config["camera"]`(누구를 보는가)와 `config["control_mode"]`(조작자 한 명 제약을 어떻게 다룰지),
그리고 `"tactics"`(택틱)는 **육성이 아니라 운용**이라 스쿼드 스펙에 적는다. 카메라는 게이지에만
붙으므로 `burst_gauge_mode: "accumulate"`인 스쿼드에서만 결과를 바꾼다 — 지금 지정된 자리는
`S36_네온리버`(리버렐리오) 하나이고, 나머지는 기본 유도(3번 자리)가 최선이거나 동률이다.
정본은 `CONTROL.md §카메라`.

#### 조건부 컨트롤 — 버스트 패턴과 같은 규칙이다

컨트롤이 조합·육성·스탯에 달린 경우도 **위 `_rules`와 똑같은 스키마**로 적는다 — 사실
같은 스키마 정도가 아니라 **같은 키**다(`apply.control`). 대상이 이름으로 정해지면 그 니케의
`data/char_defaults.json` 항목에 적고, 대상을 코드가 골라야 하면(버충 담당)
`data/tactics.json`에 적는다.

판정도 같은 자리에서 한 번에 한다(`spec.resolve_rules()`). 붙은 컨트롤은 이탈 보고에
`(레이어)`로, 어떤 택틱인지는 머리줄에 따로 실린다.

`manual` 택틱(버충)은 자동으로 붙지 않는다 — 스쿼드 스펙에 `"tactics": ["버충"]`을 적거나
CLI `--tactic 버충`으로 켠다. 이쪽은 **호출자 오버라이드로 들어가므로 이탈 보고에 `(지정)`**
으로 잡힌다. 의미·수치 근거의 정본은 `CONTROL.md §택틱` · `§부착`.

### 2.5층 — 육성 프로필 (선택, `profiles/<이름>.json`)

고정 스펙 대신 **실제 계정의 육성 상태**로 돌릴 때만 끼는 레이어다. `profile-sync` skill이
만들고(`scraper/profile_fetch.py`), `profiles/`는 통째로 gitignore인 개인 데이터다.

```bash
python -m runner.sim "<스쿼드>" --profile me      # 보고서는 스펙 JSON의 "profile": "me"
```

**2층 뒤에 오는 이유**: 2층의 장비 옵션 값은 고정 스펙을 전제로 잡힌 것이라(미하라의 23.22%는
기본 스펙에서 동률이 나지 않게 1%p 올린 값이다) 실제 계정 수치가 그걸 이겨야 한다. 반대로
컨트롤·버스트 패턴은 육성이 아니라 **운용**이라 조합·상황에 달려 있고 계정 상태로 결정되지
않는다 — 그래서 프로필은 육성 키만 담고(`spec.GROWTH_KEYS`), 운용 키가 섞여 들어오면 로드가
끊는다. 결과적으로 2층의 컨트롤은 프로필 위에서도 그대로 살아남는다.

담기는 것과 안 담기는 것:

| | | 근거 |
|---|---|---|
| 돌파·코강·호감도·스킬 레벨 | ○ | 레벨과 달리 인게임에서 고정되지 않으므로 실제 값을 쓴다 |
| **레벨** | ✗ (정책) | 아래 §레벨 정책 |
| 장비 4부위 · 오버로드 합산 | ○ | 미장착은 `tier: "없음"` — 기업 강화0과 다르다(그쪽은 플랫 스탯이 붙는다) |
| 소장품 / 애장품 | ○ | 슬롯 공유. 애장품은 스탯이 SR15와 같아 `SR15`로 적고, **단계는 `favorite_stage` 0~3으로 따로 담는다** — 단계가 스킬 판본을 정하므로 딜에 직접 걸린다 |
| 콘솔 | ○ | 전초기지 재활용 연구실. **역할군 3개·기업 5개가 따로 크므로 소속별 dict로 담는다** |
| 큐브 | ✗ | API가 장착 중인 것만 준다. 자유롭게 갈아끼우므로 육성이 아니라 케이스가 정하는 축이다 |
| 컨트롤·버스트 패턴 | ✗ | 운용이다. 2층이나 3층에 둔다 |

#### 레벨 정책 — 프로필은 레벨을 담지 않는다

인게임 캐릭터 레벨은 **동기화 소대에 넣었는지**에 달려 있다. 소대 밖이면 레벨 1로 남는데
그건 육성이 덜 됐다는 뜻이 아니라 편성을 안 했다는 뜻이고, 넣기만 하면 즉시 소대 레벨이 된다.
게다가 **솔로레이드는 레벨이 400으로 고정된다.** 그래서 레벨은 계정 상태가 아니라 러너의
정책이다 (`spec.LEVEL_MODES`):

| 정책 | 레벨 | 언제 |
|---|---|---|
| `fixed` **(기본)** | `DEFAULT_CHAR["level"]` = 400 | 솔로레이드 기준. 고정 스펙 결과와 **레벨이 같아** 육성 차이만 남는 비교가 된다 |
| `sync` | `_account.synchro_level` | 동기화 소대 레벨로 볼 때. 소대 밖 캐릭터도 같은 값으로 계산한다 |

`python -m runner.sim … --profile me --profile-level sync` / 보고서 스펙의 `"profile_level"`.

그 결과 **동기화 소대 밖 캐릭터도 정상적으로 계산된다.** `lv <= 1`은 미보유 판정이 아니다 —
실측(2026-08-15)에서 소대 밖 20종은 전부 보유 중이었고 장비까지 낀 캐릭터가 섞여 있었다.
프로필은 로스터 전원을 담고 `_unsynced`는 참고 정보로만 남는다. 대신 그쪽은 스킬 레벨이
낮은 경우가 많아, **스킬 레벨 10 미만인 스쿼드 멤버는 결과에 따로 적힌다** — 딜이 낮은 이유가
조합이 아니라 육성이라는 걸 수치만 보고 오해하지 않게.

프로필에 아예 없는 이름(미보유·수집 후 나온 신캐)은 **미육성으로 계산한다** — 돌파 0 · 스킬
1/1/1 · 장비 미장착 · 소장품 없음. 고정 스펙으로 떨어뜨리면 만렙 가상 캐릭터가 섞여
"내 계정 기준"이 거짓말이 되고, 에러로 끊으면 "지금 뽑으면 얼마나 나오나"를 물어볼 수 없다.
레벨과 콘솔은 다른 캐릭터와 같다 — 레벨은 정책이, 콘솔은 계정이 정하기 때문이다.
대체한 이름은 결과에 목록으로 실린다. 정본은 `spec.py`의 `UNGROWN`이다.

**회귀 하네스는 프로필을 받지 않는다.** `snapshot.py`는 `build_char`에 프로필을 넘기지 않으며,
golden baseline은 고정 스펙 전용이다.

### 3층 — 호출자 오버라이드

`SQUADS[*]["chars"]`는 **그 스쿼드에서만** 다른 것을 적는 자리다 (예: `S40_앨리스모더니아`의
앨리스 장전컨, `S40_홍련흑영벨벳`의 홍련 : 흑영 탄충 큐브). 어디서든 그렇게 굴리는 설정이면
`chars`가 아니라 2층에 적는다 — 같은 값을 스쿼드마다 반복하면 갈라진다.
컨트롤을 통째로 끈 대조군이 필요하면 `runner/sim.py --auto`를 쓴다.

### 이탈 보고 — 1층이 아니면 언제나 알린다

**2층·3층이 붙은 결과는 그 사실을 함께 낸다.** 수치만 보고 "기본 스펙 결과"로 읽는 게
이 프로젝트에서 가장 조용히 틀리는 경로라서, 사람의 성실성이 아니라 도구가 강제한다.

| 도구 | 어떻게 |
|---|---|
| `runner/sim.py` | 스쿼드 줄 바로 아래 이탈 목록 (이탈 없으면 "1층 그대로" 한 줄) |
| 웹앱 보고서 | 탭 상단 **접히지 않는** 경고 배너 (`spec.format_deviations()`를 그대로 싣는다) |
| `runner/snapshot.py` | `meta.spec_deviations`로 baseline에 박힌다 → **딜이 안 움직여도 레이어가 바뀌면 FAIL**. `--list`도 함께 출력 |

**Claude는 이 줄을 유저 답변에도 그대로 옮긴다.** 시뮬 결과를 보고할 때 1층이 아니었으면
어떤 레이어·오버라이드가 붙었는지 먼저 적는다. 구현은 `spec.format_deviations()` /
`spec.squad_deviations()`.

#### 프로필을 끼면 기준선이 바뀐다

육성 프로필(2.5층)을 쓰면 이탈 보고의 기준선이 `1층+레이어+프로필`이 된다. 1층을 기준으로
두면 육성 키 전부가 캐릭터마다 열 줄씩 이탈로 잡혀 **정작 봐야 할 3층 지정이 묻히기** 때문이다.
대신 프로필을 썼다는 사실 자체는 머리줄로 못박히고, 프로필이 아는 경고(소대 밖 캐릭터·애장품
단계·큐브 보유 하한 미달·미보유 대체)도 같은 자리에서 함께 나온다.

> **프로필 결과와 고정 스펙 결과의 총딜을 나란히 놓지 않는다.** 육성이 통째로 다른 두 수치라
> 차이가 조합·운용의 차이로 읽히면 안 된다. 비교는 프로필 안에서(축 하나씩) 하거나 고정 스펙
> 안에서 한다 — 러너가 이 경고를 결과마다 강제로 싣는 이유다.

즉 **하네스 총딜은 실전 기대딜이 아니다.** 스펙이 고정된 비교용 수치일 뿐이다.

## 이 도구가 하는 일과 하지 않는 일

**한다** — 변화 감지. "무엇이 이전과 달라졌는가"를 캐릭터·효과 단위로 짚는다.

**하지 않는다** — 정확성 검증. baseline을 찍는 순간 그 시점 코드의 **기존 버그도 "정상"으로 고정**된다.
정확성은 `docs/scenarios/<이름>.md`의 검증 체크리스트가 담당한다.

즉 하네스가 PASS라고 해서 계산이 맞다는 뜻이 아니다. "내가 방금 고친 것 때문에
다른 게 바뀌지는 않았다"는 뜻이다.

## 왜 결정론적인가

`simulate(..., seed=N)`을 주면 크리 판정·코어히트·`prob:N` 조건·`allies_random`이
모두 재현되어 결과가 완전히 같아진다. 프로세스가 달라도, `PYTHONHASHSEED`가 달라도 같다.

그래서 **오차 범위가 없다. 완전 일치해야 PASS다.**

> 참고 — `simulate()`의 `seed` 기본값은 `None`(시드 미고정)이다. 기대딜은 여러 회 평균이
> 맞으므로 시드를 안 주고 돌리면 매번 다른 값이 나온다(`runner/sim.py`의 기본 동작).
> 시드는 하네스·`runner/sim.py --seed`·보고서(고정 시드셋 `[1..runs]`)가 명시적으로 넘긴다.

시드가 프로세스마다 독립이라 **스쿼드를 병렬로 돌려도 결과가 같다.** `--jobs`가 그것을 쓴다.

> 시드 대신 난수를 없애는 길도 있다 — `config={"rng_mode": "expected"}`
> (CLI: `python -m runner.sim "..." --expected`). 크리·코어히트를 확률 판정 대신
> 기대값으로 태워 **1회 실행으로 기대딜**이 나온다. 반복 평균이 필요 없어 조합 비교가
> `runs`배 빨라진다. 대신 히트별 크리/코어 구분이 사라지므로(`is_crit` 항상 False,
> `hit_tag`에 `core:` 없음) 히트 로그로 크리·코어를 확인하는 검증에는 쓰지 않는다.
> 하네스 골든 스냅샷은 지금도 `rng_mode="random"` + 고정 시드로 찍는다.
> 자세한 트레이드오프는 `docs/CALCULATOR.md §기대값 모드`.

### 버프 집계 캐시 감사 — `NIKKE_BUFF_AUDIT=1`

`get_buffs()`는 `_active` 중 **시간·상태에 무관한 버프**(장비·큐브·소장품·영구 패시브 —
전체의 8할쯤)의 기여를 `_cache_version`당 한 번만 평가해 재사용한다. 이 캐시가 성립하는
전제는 하나다 — **`_active`를 바꾸면 반드시 `_invalidate_buffs_cache()`를 거친다.**

새 효과가 그 전제를 깨면 낡은 값이 조용히 계속 쓰인다. 그래서 감사 모드를 둔다:

```bash
NIKKE_BUFF_AUDIT=1 python -m runner.snapshot --squad <스쿼드>
```

매 조회마다 계획을 다시 만들어 캐시와 대조하고 다르면 즉시 `AssertionError`로 끊는다.
2배쯤 느리므로 평상시엔 끄고, **`_active`를 직접 건드리는 코드를 고쳤을 때** 한 번 돌린다.
판정은 보수적이라(`BuffManager._is_time_invariant`) 애매한 버프는 캐시에 넣지 않는다.

## 스냅샷 4층 구조 — diff 읽는 법

절대 시각은 저장하지 않는다. 발사 타이밍이 1프레임(0.0167s) 밀리는 건 노이즈지만,
**"버프가 적용된 다음에 대미지가 계산되는가" 하는 순서는 신호**이기 때문이다.

### L1 수치 — 무엇이 얼마나
캐릭터별 총딜, 스킬별 딜·히트수, `hit_tag` 분포, 크리 수, 풀버스트 횟수.

```
[L1 수치]
스쿼드 총딜  1,862,282,550 → 1,863,145,587  (+863,037, +0.05%)
[라피 : 레드 후드] 스킬 <부착형 유탄 4>  딜 225,995,644 → 226,031,557  히트 106 → 106
```
→ **L1만 움직였다면** 순수한 계수·수치 변경이다. 발동 타이밍은 그대로.

### L2 발동 횟수 — 몇 번 걸렸나
버프/인스턴트 이름별 발동 횟수와 대상 집합.

```
[L2 발동 횟수]
! 버프 [붉은 두건] 발동 12 → 9회
+ 버프 [○○] 신규 발동 4회 → ['미하라']
- 버프 [××] 발동 사라짐 (기존 30회)
```
→ **가장 먼저 볼 층.** 버프가 안 걸리게 된 회귀는 여기서 바로 드러난다.
딜이 상쇄되어 L1이 조용해도 L2는 반응한다.

### L3 순서 — 무엇 다음에 무엇이
풀버스트 진입을 경계로 사이클을 나누고, 각 사이클 안의 이벤트를 **시각 없이 순서열로** 기록.
히트는 이벤트 사이 구간의 집계로 압축한다.

```
[L3 순서]
── 사이클 1 순서 변화 ──
   B+ 릴렉스 → 크라운
  -HITS 라피 : 레드 후드:1 crit:0 core:0
  +HITS 라피 : 레드 후드:3 crit:0 core:0
   B- 터진 거품 2 → __enemy__
```
표기: `B+` 버프 활성 / `B-` 버프 만료 / `I` 인스턴트 / `BURST` 버스트 이벤트 / `HITS` 구간 히트 집계.

→ **버프와 히트의 상대 순서**가 바뀌면 여기서 잡힌다. 1프레임 밀림은 diff를 만들지 않지만,
버프가 히트보다 뒤로 밀리면 즉시 드러난다.

### L4 위상 — 정수 지표
사이클 간격(0.05초 정밀도)과 "버프 발동 → 대상의 다음 히트까지 프레임 수" 분포.

```
[L4 위상]
사이클 간격  [12.55, 12.55, ...] → [12.55, 17.30, ...]
버프 [○○] 발동→다음히트  3프레임 11→8, 4프레임 22→25
```
→ 사이클 간격이 12.5초에서 크게 벗어나면 버스트 사이클이 깨진 것이다.

## baseline 갱신 규칙

`baseline/*.json`은 **자동 생성물이다. 손으로 편집하지 않는다.**

FAIL이 났을 때:

1. diff를 **그대로 유저에게 보고**한다. 재시도하지 않는다.
2. 유저가 "그 변화는 의도한 것"이라고 확인해준 뒤에만 `--update`.
3. 의도치 않은 변화면 회귀다 — 원인을 찾을 때까지 갱신하지 않는다.

스쿼드를 추가하려면 `runner/snapshot.py`의 `SQUADS`에 항목을 넣고
`--update --squad <이름>`으로 baseline을 만든다.

> **baseline 세대 경계 — 2026-08-07 기본 스펙 전환.** 그날 25스쿼드 baseline을 전부
> 새로 찍었다(커밋 `c0a0b0a`). 종전에는 장비 옵션이 하나도 없는 스펙으로 돌렸으므로
> **그 이전 총딜·델타는 지금 값과 직접 비교되지 않는다.** 옛 문서·커밋 메시지에서
> 총딜 수치를 인용할 때는 이 경계를 먼저 본다.

과거 baseline 갱신 내역은 이 문서가 아니라 **git log**가 정본이다
(`git log --oneline -- baseline`). 변경 사유·수치 근거는 해당 커밋 메시지와
`docs/scenarios/*.md`에 있다.

## 스쿼드 커버리지

스쿼드 목록·커버 인원·미커버 명단은 `python -m runner.snapshot --list`가 **정본**이다 —
목록 끝에 함께 출력한다 (`snapshot.coverage()`). 스쿼드도 캐릭터도 계속 늘어나므로
**개수를 문서에 옮겨 적지 않는다.** 아래 표는 각 계열이 무엇을 커버하는지만 적는다.

| 스쿼드 | 성격 |
|--------|------|
| `S36_*` ~ `S40_*` | **enikk.app 솔로레이드 시즌 36~40의 실사용 조합 그대로.** 앞머리 숫자가 그 시즌이고, 시즌이 곧 적 코드다(아래 §적 속성). 각 스쿼드 주석의 "N파스"가 실사용 횟수다 |
| `커버_*` | 실전 덱에 한 번도 안 나오는 캐릭터만 모은 **지정 편성**. 실사용 기록이 없으므로 딜 순위를 실전과 견주는 근거로 쓰지 않는다 — 커버와 변화 감지 전용이고, 늘어날수록 하네스가 실전에서 멀어지므로 최소로 둔다 |

**인공 편성(구 `지그_*`)은 없앴다.** 코드 경로를 붙잡으려고 만든 스쿼드가 따로 있었는데,
실전 조합으로 다시 짜 보니 그 경로를 실전 덱이 그대로 밟는다 — `element_code_override`와
라피 : 레드 후드의 `no_burst1_ally` → `전투 보조` 전환은 `S36_질미하라`·`S38_델타레이`가,
라이프스틸 자급(`lifesteal_pct` → `event:heal_received`)은 `S40_아스카`가, 방무 조합은
`S39_라플라스리코리코`가 받는다. `test_B3` 더미도 더는 쓰지 않는다.

> 실전 조합이 곧 코드 경로를 덮는 것은 **우연이고, 보장이 아니다.** 시즌이 바뀌어 조합을
> 갈아엎을 때 위 경로가 어느 스쿼드에도 없게 될 수 있다. 조합을 바꾸기 전에 이 절과
> `snapshot.py` 헤더의 조건·컨트롤 지도를 먼저 읽는다.

### 적 속성 (`enemy` 키)

스쿼드 dict의 `enemy`는 `simulate(enemy=...)`로 그대로 넘어간다 (`DEFAULT_ENEMY` 오버라이드).
**키가 없으면 무속성 적**이라 `is_element_match`(DealForm ⑦)가 영구 거짓이다.

작열 약점 솔로레이드는 `{"code": "풍압"}`이다 — 적 코드에 **우월한** 캐릭터가 유리를 받으므로
(작열 → 풍압, `damage._CODE_ADVANTAGE`), "작열 약점"은 적 코드가 풍압이라는 뜻이다.
이때 작열 캐릭터의 딜은 ×1.2909가 된다 (⑦ 기본 +10% + 기본 스펙의 공통 큐브 Lv15 우월코드 대미지 19.09%).

**코드는 시즌이 정한다.** 스쿼드 이름 앞머리를 보면 바로 안다:

| 시즌 | 보스 | `enemy.code` | (약점) |
|---|---|---|---|
| S36 | Egovista | `수냉` | 전격 |
| S37 | Ultra | `작열` | 수냉 |
| S38 | Annihilio | `철갑` | 풍압 |
| S39 | Island Eater | `전격` | 철갑 |
| S40 | Luxurious Spider | `풍압` | 작열 |

**무속성 적은 `커버_라플라스맥스웰` 하나뿐이다.** `is_element_match`가 영구 거짓인 경로가
거기서만 스냅샷에 들어온다 — 코드를 붙이면 그 분기가 죽어도 하네스가 못 잡는다.

`element_code_override`(로스터 코드가 아니라 버프로 성립하는 우월 코드 — 라피 : 레드 후드
`부착형 유탄`)는 라피가 낀 코드 스쿼드 전부가 밟는다. `no_burst1_ally` → `전투 보조` 전환까지
함께 밟는 것은 팀에 고정 B1이 없는 `S36_질미하라`·`S38_델타레이` 둘이다.

### 코어·파츠·적정거리 (`enemy` 나머지 키)

**시즌과 무관하다.** 그 경로를 밟을 baseline이 필요해서 켜는 것이고, 켠 자리마다 이유가
`snapshot.py` 주석에 있다. 옮기거나 지우면 해당 경로가 죽어도 하네스가 못 잡는다.

| 키 | 켜 둔 자리 | 지키는 것 |
|---|---|---|
| `core_px` | `S36_트리나홍련`·`S40_토브드레이크` 52 · `S38_델타레이` 30 | 코어히트율 확률 계산과 `core_dmg_pct`. `_core_hit_prob`가 직경에 비선형이라 값을 둘로 나눴다 |
| `has_parts` | `S39_크리스탈이브` · `S39_라플라스리코리코` · `S38_사쿠라로산나` · `S40_민트디젤` · `S40_킬러와이프` | `part_hit_count:N` 라우팅(`squad_body_hit` → `squad_part_hit`)과 `part_dmg_pct`의 전제 |
| `part_break_interval` (config) | `S38_사쿠라로산나` 30초 · `S40_민트디젤` 60초 | `event:part_destroy`. 주기를 달리 둬 사이클 대비 위상이 서로 어긋나게 했다 |
| `optimal_range_weapons` | `S38_누아르` `["SG"]` · `S39_마르차나아쿠아` `["SMG"]` · `S40_퀸유키코` `["SG","SMG"]` | ③의 고정 +30%. **일반 공격에만** 붙고 스킬에는 안 붙는다 |

> **`part_dmg_pct`는 조건 셋이 다 맞아야 딜에 실린다** — `has_parts` + 원문이 파츠를 명시한
> damage 효과(`hits_parts`) + 그 효과의 발동 조건. 로스터에서 `hits_parts`를 가진 것은
> 신데렐라 : 크리스탈 웨이브 `모드 스왑 2` 하나뿐이고 저격 모드를 요구한다. 그래서
> `S39_크리스탈이브`는 `chars`로 `weapon_mode_swap`까지 켠다. **`has_parts`만 켜면 총딜이
> 1원도 안 움직인다** — 레이븐 `급소 공략`·스노우 화이트 : 헤비암즈 파츠 대미지가 무효인 것도
> 같은 이유다(`IMPL-STATUS.md`).

### 컨트롤은 어디에 있나

**컨트롤 전용 스쿼드는 없다.** 캐릭터별 기본 레이어가 붙여 주거나(`data/char_defaults.json`),
그 조작이 실전인 조합의 `chars`에 직접 적는다. 엄폐컨·홀드컨은 2026-08-07에 조건부 레이어로
내려갔으므로 미란다가 함께 있는 것만으로 켜진다.

`CONTROL.md`의 설정 키가 전부 덮이도록 **일부러 흩어 놨다.** 아래 자리를 옮기면 그 키가
죽어도 하네스가 못 잡는다.

| 설정 | 켜 둔 자리 |
|---|---|
| 톡톡이 `tap_fire` | 앨리스(`S40_앨리스모더니아`) · 아인(`S36_아인루주`) · 밀크 : 블루밍 바니(`S39_밀크도라`, `full_charge_interval`까지) — 전부 레이어 |
| 장전컨 A `before_fb_end` | `S38_델타레이` 한 자리에서 `lead`·`duration`까지 (라피 : 레드 후드, `chars`). **상수 경로 커버가 목적이고 실전 권장이 아니다** — 고정 시간이 충전 창을 먹는다(cf0ef28) |
| 장전컨 B `into_fb` | `S40_앨리스모더니아` (앨리스, `margin`) |
| 장전컨 C `finish_by_fb_end` | `S39_나가라피` · `S37_브래디퀀시` · `S40_브리드라피` (셋 다 라피 : 레드 후드 + `if_dry`, `chars`) |
| 장전컨 D `finish_by_own_buff_end` | `S37_일레그루드밀라` — 루드밀라 : 윈터 오너의 `이끄는 등불 2` 만료 전에 재장전을 끝낸다 (`buff`·`margin`, `chars`) |
| 탄충 취소 `cancel_on_full` | 홍련 : 흑영(`S40_홍련흑영벨벳`, 레이어) |
| 엄폐컨 `cover` | 기본형 `S40_킬러와이프`(미하라 : 본딩 체인 + 미란다, 레이어) · `extend` `S40_브리드라피`(`chars`) |
| 홀드컨 `own_full_burst` | `S36_아인루주` — 아인+에이다, 에이다+미란다 두 조건부 규칙이 한 스쿼드에 함께 걸린다 |
| 홀드컨 `charge_hold_after_fb` | 밀크 : 블루밍 바니(`S39_밀크도라`, 레이어). 차지형 전용 정책 |
| 홀드컨 `burst_chain` + `hold_until_close` | 스노우 화이트 : 헤비암즈(`S36_질미하라`, fixed/RL) · 헬름(`S39_마르차나아쿠아`, accumulate/SR) |
| 명시 시퀀스 `sequence` | 벨벳(`S38_마나`, `chars`) |

설정값의 의미·손익 판단 기준은 `CONTROL.md`가 정본이다. `reload.margin`처럼 조합마다
다시 재야 하는 값은 `snapshot.py`의 해당 스쿼드 주석에 근거를 적어 둔다.

> **명시 시퀀스는 절대 시각이라 편성에 매인다** (`CONTROL.md §명시 시퀀스`). `S38_마나`의
> 멤버를 건드리면 사이클이 밀려 시퀀스가 엉뚱한 구간에 떨어진다 — 그 스쿼드는 편성을 고정한다.

> **동시 컨트롤 1명 제약은 검사하지 않는다** (`CONTROL.md §미구현`). 한 스쿼드에 둘을 켜면
> (`S40_브리드라피`의 라피 장전컨 + 미하라 엄폐컨) 실전에서는 한 명만 조작할 수 있으므로
> **낙관적인 상한**이다.

`chars` 키는 그 스쿼드에서만 컨트롤을 켜거나, 정책이 의미를 갖는 데 필요한 설정을 주는
용도다. **기본 스펙·레이어로 표현되는 것은 쓰지 않는다.**

조연은 임의 편성이 아니라 **실제 상위 조합 그대로**다. 따라서 실전에서 실제로 맞물리는
버프 상호작용까지 스냅샷에 들어온다. 대신 조합을 바꾸면 baseline이 통째로 흔들리므로,
**커버 대상만 보고 조연을 갈아끼우지 않는다.**

### 버스트 게이지 실누적(`accumulate`)은 어디에 있나

기본값은 `fixed`(캐릭터별 `burst_regen_time`의 고정 시각)다. 실누적 모델
(`docs/mechanics/버스트 게이지.md`)은 **아래 8스쿼드에서만** 돈다 — `config`에
`"burst_gauge_mode": "accumulate"`로 켠다.

전 스쿼드를 실누적으로 돌리지 않는 이유는 두 모델을 나란히 지키기 위해서다. 반대로
8개를 0개로 줄이면 게이지 식·아군 가산·카메라가 통째로 죽어도 하네스가 못 잡는다
(2026-08-29 이전이 정확히 그 상태였다).

| 스쿼드 | 밟는 경로 |
|---|---|
| `S39_나가라피` | 시전자 기준 가산 · 일반 공격 명중 전환 · 라피 유탄 예외 · 버충 컨트롤 · 카메라 유도가 전부 걸린다. **유저 실측(180초 15버스트)이 붙어 있는 유일한 조합** |
| `S40_브리드라피` | 아니스 : 스타가 3번 자리가 아닌 곳. 카메라와 시전자 기준 가산이 겹치는 신호가 위와 다르다 |
| `S38_마나` | 마나 `매터 시그마` 본인 대상 시전자 기준 가산 + 리틀 머메이드 「충전 37%」 무관 경로 |
| `S39_마르차나아쿠아` | 헬름 `진두지휘 3`의 「충전 14.31%」 = `handle_burst_charge_pct` (`full_charge_hit` 트리거) |

### 스쿼드를 새로 추가할 때

> **시작 전 필수** — `docs/GAMEPLAY.md`의 `## 스쿼드 구성` 절을 읽는다.
> (§유효한 스쿼드의 조건 / §버스트 쿨타임 감소 / §**버스트 사용 순서와 배치** / §더미 캐릭터)

특히 다음 두 가지는 이 하네스를 만들면서 실제로 밟은 함정이다.

- **멤버 순서 = 버스트 사용 순서다.** 같은 단계에 둘 이상이면 앞사람이 선점한다.
  뒤로 밀린 쪽은 **버스트를 한 번도 못 쓴 채** 스냅샷이 찍힌다.
  실전 조합은 순서까지 실사용 기록이라 재정렬하지 않으므로, 대신 아래 `burst_pattern`으로
  사이클을 나눈다. 초기 배치에서 소다·델타·헬름:아쿠아마린·나가·벨벳·프리카 6명이
  이 상태였고, 지금은 `S39_나가라피`·`S38_델타레이` 등이 패턴으로 해결한다.
- **레드 후드(`burst_stage: "A"`)의 단계를 고정하지 않는다.** 고정하면 라피 : 레드 후드의
  `no_burst1_ally` 조건이 깨져 라피의 1버 전환이 막힌다. 배치 순서로만 조정한다.
  팀에 라피가 없으면 레드 후드가 **한 사이클에 1단계와 3단계를 혼자 겸할 수 있다** —
  `S39_레이븐레드후드` 2번째 칸이 `20.4`로 튀는 이유가 그것이고, 정상이다.

그 밖에:

- 버스트를 안 쓰는 캐릭터는 `config={"no_burst_char": "이름"}`. 한 명만 지정할 수 있다.
  (`S40_토브드레이크`의 솔린 : 프로스트 티켓 — 실전 운용, `S36_블랑`의 루주 — 사이클 안정화)
- **특정 캐릭터를 N사이클마다만 버스트**시키려면 `config={"burst_pattern": {...}}`.
  값은 `"every:N"`(N의 배수 사이클) 또는 사이클 번호 목록이다. 목록은 1-based이고
  사이클 수(180초 ÷ 사이클 간격)보다 넉넉히 잡는다 — 모자라면 그 뒤로는 등급 2(맨 뒤)가 된다.
  - 같은 단계 둘을 반씩 나누기: 뒷사람에게 `"every:2"` (`S39_나가라피`의 나가)
  - 셋을 3등분: `[1,4,7,…]` / `[2,5,8,…]` / `[3,6,9,…]` (`S37_일레그루드밀라`)
  - 캐릭터에 고정된 패턴(마스트 : 로망틱 메이드 `3의 배수` 등)은 **레이어가 붙인다** —
    `data/char_defaults.json`의 `_burst_patterns`·`burst_pattern`. 스쿼드에 다시 적지 않는다.
- 사이클별 순서를 통째로 못 박아야 하면 `config={"burst_sequence": [...]}`. 엔트리마다
  **1·2·3단계를 전부** 적는다 — 빠진 단계는 후보 0명이 되어 영구 블록된다
  (`_next_action_t = inf`). `burst_sequence`가 있으면 `burst_pattern`은 무시된다.
  현재 쓰는 스쿼드는 없다.
- 버스트 단계·쿨다운은 `data/parsed_nikke.json`의 `burst_stage` / `burst_cooldown`.
- `test_B3` 같은 더미는 더는 쓰지 않는다. 실전 조합에는 빈 자리가 없다.

- **볼륨·리타·헬름 : 아쿠아마린** — `full_burst_start_count:1/2/3` 트리거라 처음 세 사이클만

- **D : 킬러 와이프·루주** — 버쿨감이 `full_charge_count:8` 트리거라 버스트 사이클과 주기가

- **아르카나+이사벨** — 버스트가 약 5초 만에 끝나고 버쿨감이 한 번 더 들어가 교대가 계속된다.

  버쿨감이 아니라 **배치** 문제라 위 표에 넣지 않는다 —
  `GAMEPLAY.md §스쿼드 구성 §버스트 사용 순서와 배치`.
