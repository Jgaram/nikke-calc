# 사이트 속도 2차 — 서버를 Bun + Hono로 교체 (결정 2026-08-26)

작성 2026-08-26, 후보 재검토·**결정** 2026-08-26. **사용자 결정: (B) Bun + Hono로 간다.**
근거: 서버-코어를 같은 언어로 묶는 이점은 운영 축뿐이고 속도 체감이 없다(경계 비용 1ms 미만 vs 요청
80~140ms) → 그 이점보다 개발 속도(AI 작성 반복 루프·자료 밀도)와 TS 선호가 크다. **계산 코어는 그대로 둔다**
— TS로 옮기면 5~20× 느려지고, 골든 비트 검증(int/float 구분)은 수 타입이 하나뿐인 JS로 재현 불가다.
단일 사용자 체감은 1차로 이미 끝났다(1덱 0.08~0.14초) — 2차가 사는 것은 동시 처리량·유지보수·개발 속도다.
착수 시기는 사용자 지시로 정한다(§3의 시기 절충 참고). 실행 계획은 §4.

## 0. 지금 서버가 어떻게 생겼나 (1차 반영 뒤)

- `web/server.py` 하나(약 2,200줄): 파이썬 표준 `http.server`(스레드 서버) — 정적 서빙(`web/dist`),
  `/api/sim`(**동기 응답** — 요청의 덱 전부를 코어 요청 배치(`run_jobs_native` → `simcore.run_request_batch`) 한 번으로
  계산해 그 응답에 담는다; 입장 제한 `SIM_SLOTS=1`·대기 12·최대 30초), `/api/fetch`(블라링크 프록시, SSE는
  여기만 남음), `/api/share`(sqlite), `/api/board`(피드백), `/api/stats`·`/admin`(테일넷 전용), `/api/cp`,
  얼굴/총딜 판독(OpenCV HOG+SVM), OG 이미지, 봇 차단·요청 빈도 제한(429).
- systemd 하드닝(`deploy/nikke-decklab.service`), Cloudflare Tunnel + Tailscale Funnel. 서버는 Oracle A1
  aarch64 4코어.
- 한계: GIL(스레드가 많아도 파이썬 코드는 한 번에 하나), 연결당 스레드, 계산 입장 제한이 한 번에 한 요청.
  **계산 자체는 이미 네이티브 코어가 하므로 병목이 아니다** — 남은 건 HTTP를 받는 껍데기다.
- 즉 «계산 경로»는 이미 후보 (A)와 같은 모양(코어 in-process)이고, 이 문서가 바꾸려는 것은 그 앞의
  **웹 서버 층**이다.

## 1. 목표와 기준

- 목표: 동시 사용자 수백 명, 초당 수십 건의 계산 요청(요청당 최대 20덱 배치)에서도 대기 없이 답한다.
  정적·SSE·API가 스레드 수에 묶이지 않는다. 메모리 상주 작게.
- 20덱 배치 산수: 코어 36~45ms/덱 → 4코어 전부 쓰면 요청당 ≈ 0.2~0.25초, 초당 ≈ 4건의 20덱 요청(코어 포화).
  그 이상은 코어를 더 빠르게 하거나 코어가 더 많은 서버가 필요하다 — 프레임워크로는 못 넘는 한계다.
- **착수 기준**(측정으로 정한다): `oha`/`hey`로 `/api/sim` 부하를 걸어 p95 지연이 코어 시간의 2배를 넘거나
  CPU가 남는데도 처리량이 안 오르면 프레임워크 병목이다. 그 전엔 안 한다.

## 2. 후보 (2026-08-26 재검토)

전제 갱신 둘. ① **스펙 조립은 이제 옮길 필요가 없다** — 1차에서 코어가 원 요청(이름·프로필·컨트롤·적·설정)을
직접 받아 조립·계산·요약까지 한다. 서버와 코어의 경계는 `run_request_batch(jobs)` JSON **하나**로 고정돼
있고, 어느 후보로 가든 이 경계를 그대로 옮기면 된다. ② **Bun은 1.4(2026-07)부터 러스트로 전면 재작성됐다**
(2025년 말 Anthropic 인수, v1.3.14가 마지막 Zig판; 6개 플랫폼 — Linux ARM64 포함 — 검증 뒤 머지, 공개 회귀
19건은 수정됨). 종전 표의 «Bun은 Zig» 전제는 낡았다. 단, **런타임의 구현 언어와 앱의 언어는 다른 층이다** —
Bun 위의 앱은 여전히 TS고, 코어는 FFI 경계(C ABI cdylib 또는 napi)를 건너 부른다.

| | (A) 러스트 axum + 코어 직접 호출 | (B) Bun + Hono(TypeScript) + 코어 FFI | (C) 파이썬 ASGI(FastAPI + uvicorn/granian) |
|---|---|---|---|
| 계산 경로 | 코어를 **in-process**로(바인딩·JSON 왕복 없음) | `bun:ffi`/napi로 요청 배치 한 함수 호출 — 경계 비용 ms 이하, 실질 동급 | 지금과 같음(in-process 바인딩) |
| 정적·SSE·동시성 | 최고. 비동기, 연결 수천 | 우수. 비동기, 연결 수천 | 좋음(비동기). 파이썬 코드는 여전히 GIL |
| 다시 짜야 할 것 | 라우트 전부 + 판독(OpenCV)은 **파이썬 사이드카** | 라우트 전부(TS) + 판독 사이드카 | 라우트 이식만(로직 재사용), 판독 그대로 |
| 언어·배포 | 코어와 한 언어, **바이너리 하나**(런타임 불요) | TS — 사용자 선호. 런타임(Bun 1.4, 러스트) 설치 필요 | 파이썬 그대로 |
| 성숙도 위험 | 낮음(axum은 오래됨; 코어 도구는 서버에 이미 있음) | 1.4가 갓 나온 대규모 재작성(2026-07) — **서버가 바로 aarch64**라 몇 달 숙성 뒤가 안전 | 낮음 |
| 작업량(대략) | 1~2주(조립 포팅이 빠져 종전 추정보다 준다) | 1~2주(같은 이유) | 3~5일 |
| 처리량 기대 | 파이썬 대비 10~50× | 5~20× | 2~5× |

## 3. 결정과 시기

- **(B) Bun + Hono 확정** (사용자 결정 2026-08-26). §2의 표는 결정 근거 기록으로 남긴다.
- **런타임: Bun 1.4.x로 바로 간다** (사용자 결정 2026-08-26 — «숙성 대기 없이 1.4대로»). 코어 바인딩이
  Node-API(napi)라 Hono 멀티런타임 특성상 **같은 코드가 Node LTS에서도 그대로 돈다** — 이건 배포 경로가
  아니라 **비상 되돌리기**로만 유지한다(Bun에서 문제가 나면 유닛의 실행줄만 node로 바꾼다). Bun 전용
  기능(bun:sqlite 등)을 쓰는 자리는 Node 폴백이 살도록 얇은 어댑터로 감싼다.
- 착수 직전 반나절 스파이크는 유지: `/api/sim`·정적·`/api/share` 세 라우트만 세워 `oha` 부하 + 코어 호출
  왕복을 재고 시작한다(설계 확인용).

**진행(2026-08-26)**: 0(계약 박제 `SERVER-CONTRACT.md`) · 1(코어 Node-API 바인딩 — PyO3와 300건 문자열 동일) ·
2(수직 슬라이스: 공통 계층 + 정적 + `/api/health` + `/api/sim`) · **3의 1묶음(공유 sqlite·피드백 보드·관리자·
운영 지표)** 완료. 회귀 `deploy/compare_servers.py` 40케이스 + 시나리오 2(공유 수명주기·보드 흐름)가 파이썬
서버와 전부 일치 — **Bun 1.4.0(배포 런타임)**과 Node 번들(비상 폴백) 둘 다. **3의 2묶음(사이드카
프록시 — cp·atk·판독·조회와 job events/result: 기존 파이썬 서버를 내부 포트로 띄워 투명 통과, SSE 실시간
검증, 사이드카 다운 시 그 라우트만 502 강등)도 완료** — 회귀 52케이스+시나리오 2 전부 일치. 남은 것:
소킹 → 서버에 Bun 설치(버전 고정)·유닛 2개(새 서버 + 사이드카)로 전환.

0. **계약 고정이 첫 단계다**: `SITE.md` §6 파일 지도 + `server.py`의 `do_GET/do_POST` 분기 전수 조사 →
   라우트별 요청/응답 JSON·상태코드·오류 문장(i18n 카탈로그 원문)을 표로 박제. 프론트는 무변경이 목표.
1. **코어 바인딩**: 코어를 Node-API 모듈(중립 이름, 예: `simcore.node`)로 노출 — 지금 파이썬 바인딩과 같은
   면(데이터 로딩 + 요청 배치 `run_request_batch` JSON in/out). Node-API를 1지망으로 하는 이유는 ① 경계
   너머 오류를 안전하게 예외로 바꿔 주고 ② Node 폴백(§3)이 공짜라서다. 문제가 생기면 `bun:ffi`(C ABI)로
   폴백. 호출은 비동기 태스크로 — 이벤트 루프를 계산이 막지 않게. 배치 병렬은 코어 스레드 풀 그대로.
2. **수직 슬라이스 먼저**: 정적 서빙 + `/api/sim`(동기, 입장 제한 세마포어 + 429)만 Hono로 세우고
   회귀·부하(스파이크)로 확인. 여기까지가 전체 위험의 대부분을 태운다.
3. 나머지 라우트: `/api/fetch`(블라링크 프록시 + SSE + 단일 비행 큐), `/api/share`(sqlite — Bun이면
   `bun:sqlite`, Node면 `better-sqlite3`), `/api/board`, `/api/stats`·`/admin`(테일넷 헤더 판정), `/api/cp`,
   봇 차단·빈도 제한, OG 이미지(`sharp`/`satori` 또는 사이드카).
4. 판독(얼굴·총딜 OCR): 파이썬 사이드카로 분리(unix socket, JSON), 서버는 프록시. 전투력 계산은 코어/TS 중
   가까운 쪽으로.
5. **회귀 스크립트가 안전망이다**: 파이썬 서버와 새 서버를 다른 포트에 같이 띄우고 같은 요청 모음(계산·공유·
   프록시·오류 경로)을 쏴 **정규화 JSON 비교** — 코어 골든 검증에서 쓴 방식 그대로. 이게 있어야 AI가 빠르게
   짜도 안전하다.
6. 배포: 런타임(Node LTS → 추후 Bun 스위치) + TS 번들 + `web/dist` + 사이드카, systemd 유닛 두 개(하드닝
   동급). **되돌리기 = 유닛 스위치**(파이썬 서버는 지우지 않고 남긴다).
7. 규모 감: 코딩 자체는 며칠, 계약 조사·회귀·소킹 포함 1~2주.

## 5. 위험·주의

- 공개 저장소·중립 이름 원칙은 그대로(코어가 무엇으로 짜였는지 API·파일명에 드러내지 않는다).
- 개인정보: 계산 요청에 실려 오는 스펙은 어느 프레임워크에서도 **저장하지 않는다**(PRIVACY.md).
- 하드닝(ProtectSystem 등)은 바이너리·런타임에도 그대로 건다. 사이드카는 같은 수준으로.
- 서버가 aarch64 — Bun은 **버전 고정**으로 설치하고, 비상 되돌리기(§3: node 실행줄·파이썬 서버 유닛)를 유지한다.
- 코어(러스트)는 이 계획의 대상이 아니다 — 바인딩 면만 늘리고 계산·검증 체계는 그대로.
- 프레임워크 교체는 «속도»보다 «동시 처리량»을 위한 것이다 — 단일 사용자 체감(1덱 0.08~0.14초)은 더 안
  빨라진다. 기대치를 여기 맞춘다.
