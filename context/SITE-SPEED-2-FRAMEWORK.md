# 사이트 속도 2차 — 서버 프레임워크 교체 (빠르고, 대용량 처리에 강하게)

작성 2026-08-26. **계획만** — 1차(`SITE-SPEED-1-RESULT-PIPELINE.md`)가 끝나고 부하 측정으로 «프레임워크가
병목»임이 보일 때 착수한다. 지금은 계산 지연의 대부분이 가공·대기(1차)라 프레임워크를 바꿔도 체감이 거의 없다.

## 0. 지금 서버가 어떻게 생겼나

- `web/server.py` 하나: 파이썬 표준 `http.server`(스레드 서버) — 정적 서빙(`web/dist`), `/api/sim`(계산,
  작업 큐 + `ProcessPoolExecutor` 워커 3 + `SIM_SLOTS=1`), `/api/sim/events`(SSE), `/api/fetch`(블라링크
  프록시, 단일 스레드 큐), `/api/share`(sqlite), `/api/board`(피드백), `/api/stats`·`/admin`(테일넷 전용),
  `/api/cp`(전투력 계산), 얼굴/총딜 판독(OpenCV HOG+SVM), OG 이미지, 봇 차단·요청 빈도 제한(429).
- systemd 하드닝(`deploy/nikke-decklab.service`: ProtectSystem=strict, StateDirectory 하나만 쓰기 등),
  Cloudflare Tunnel + Tailscale Funnel.
- 한계: GIL(스레드가 많아도 파이썬 코드는 한 번에 하나), 연결당 스레드, 수동 작업 큐(계산은 한 번에 한
  요청), SSE 연결이 많아지면 스레드가 그만큼 잡힌다. 계산 코어는 이미 네이티브라 «계산» 자체는 병목이 아니다.

## 1. 목표와 기준

- 목표: 동시 사용자 수백 명, 초당 수십 건의 계산 요청(요청당 최대 20덱 배치)에서도 대기 없이 답한다.
  정적·SSE·API가 스레드 수에 묶이지 않는다. 메모리 상주 작게.
- 20덱 배치 산수: 코어 45ms/덱 → 4코어 전부 쓰면 요청당 ≈ 0.25초, 초당 ≈ 4건의 20덱 요청(코어 포화).
  그 이상은 코어를 더 빠르게 하거나 코어가 더 많은 서버가 필요하다 — 프레임워크로는 못 넘는 한계다.
- 착수 기준(측정으로 정한다): 1차 뒤 `oha`/`hey`로 `/api/sim` 부하를 걸어 p95 지연이 코어 시간의 2배를 넘거나
  CPU가 남는데도 처리량이 안 오르면 프레임워크 병목이다. 그 전엔 안 한다.

## 2. 후보

| | (A) 러스트 axum/actix + 코어 직접 호출 | (B) Bun + Hono(TypeScript) + 코어 FFI | (C) 파이썬 ASGI(FastAPI + uvicorn/granian) |
|---|---|---|---|
| 계산 경로 | 코어를 **in-process**로 부른다(PyO3·JSON 왕복 없음, 스레드 풀 rayon) — 가장 빠르다 | `bun:ffi`로 코어 cdylib(C ABI `simulate_json`)를 부른다, 워커 스레드 | 지금과 같음(PyO3) |
| 정적·SSE·동시성 | 최고. 비동기, 연결 수천 | 우수. 비동기, 연결 수천 | 좋음(비동기). 파이썬 코드는 여전히 GIL |
| 다시 짜야 할 것 | 라우트 전부 + 스펙 조립(`build_squad`) 포팅 + 판독(OpenCV)은 **파이썬 사이드카** | 라우트 전부 + 스펙 조립 포팅(TS) + 판독 사이드카 | 라우트 이식만(로직 재사용), 판독 그대로 |
| 언어 | 코어와 같다(러스트 하나로 통일) | TS — 사용자 선호(Bun). ※ Bun은 Zig로 짜였다(러스트 아님) | 파이썬 그대로 |
| 작업량(대략) | 2~3주 | 2~3주 | 3~5일 |
| 처리량 기대 | 파이썬 대비 10~50× | 5~20× | 2~5× |

스펙 조립(`context/spec.py build_squad/build_config`, 프로필→덱 스펙 병합)은 A·B 모두 옮겨야 한다.
러스트 코어에 이미 `spec.rs`(조립된 스펙 파싱)가 있으므로 A가 조립까지 옮기기 쉽고, 하네스 `assemble`
케이스(입력 = 조립된 스쿼드)로 조립 결과를 비트 검증할 수 있다.

## 3. 권장 순서

1. **1차 먼저.** 그 뒤 부하 측정(§1 기준)을 남긴다.
2. 병목이면 **(A) 러스트 axum**을 권한다 — 코어와 한 언어, 계산이 in-process(요청당 JSON 왕복·프로세스
   풀 제거), 배포 산출물이 바이너리 하나(systemd 하드닝 그대로). 판독(OpenCV)만 파이썬 사이드카
   (unix socket)로 남기고, 나중에 러스트로 옮길지 정한다.
3. 사용자가 TS를 원하면 (B). 코어는 C ABI 한 함수(`simulate_json`)만 내면 되고, Hono 라우트는 얇다.
   단 «Bun이 러스트»라는 전제로 고르지는 않는다.
4. 최소 비용으로 동시성만 올리고 싶으면 (C).

## 4. (A)로 갈 때의 단계

1. 라우트 목록·계약 고정: `SITE.md` §6 파일 지도 + `server.py`의 `do_GET/do_POST` 분기 전수 조사 →
   요청/응답 JSON을 그대로 유지(프론트 무변경). 오류 문장은 i18n 카탈로그와 같은 원문.
2. 스펙 조립 포팅(`spec.rs` 확장) → 하네스로 검증(입력 names/over/profile → 조립 스쿼드 비트 동일).
3. 계산 경로: 코어를 rayon 스레드 풀로(스레드-로컬 `Data`), 요청당 큐 없이 즉시. 대량 요청 보호는
   세마포어(동시 N개) + 429.
4. 공유 링크(sqlite, `rusqlite`), 피드백 보드, 통계·admin(테일넷 헤더 판정), 봇 차단·빈도 제한, OG 이미지
   (지금 파이썬 PIL → 러스트 `image`/`resvg` 또는 사이드카).
5. 판독(얼굴·총딜 OCR, 전투력 계산): 파이썬 사이드카로 분리(unix socket, JSON), 서버는 프록시.
6. 배포: 바이너리 + `web/dist` + 사이드카. systemd 유닛 두 개. 되돌리기는 유닛 스위치.
7. 검증: 기존 서버와 **같은 요청·같은 응답**(정규화 JSON 비교) 회귀 스크립트, 부하 측정 전후 비교.

## 5. 위험·주의

- 공개 저장소·중립 이름 원칙은 그대로(코어가 무엇으로 짜였는지 API·파일명에 드러내지 않는다).
- 개인정보: 계산 요청에 실려 오는 스펙은 어느 프레임워크에서도 **저장하지 않는다**(PRIVACY.md).
- 하드닝(ProtectSystem 등)은 바이너리에도 그대로 건다. 사이드카는 같은 수준으로.
- 프레임워크 교체는 «속도»보다 «동시 처리량»을 위한 것이다 — 1차로 덱당 60ms가 되면 단일 사용자 체감은
  더 안 빨라진다. 기대치를 여기 맞춘다.
