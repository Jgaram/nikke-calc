# 계산 엔진 가속 검토안 (2026-08-25, 미적용)

상용 서버에서 덱 하나(180초 전투)에 **약 3초**가 든다. 이 문서는 «어디서 시간이 가고,
무엇을 고치면 얼마나 빨라질 수 있으며, 어떻게 결과가 같음을 증명할지»를 적어 둔 검토안이다.
**아무것도 적용하지 않았다.** 적용은 §5의 검증을 전부 통과한 뒤에만 한다.

## 1. 측정한 것

| 항목 | 값 |
|---|---|
| 서버 | Oracle A1.Flex 4 OCPU(ARM Neoverse-N1)·24GB·GPU 없음 |
| 덱 하나 | CPython 3.12: **1.8~3.0초**(고정 스펙), 실제 프로필 평균 **3.3초** (17분간 290덱 누적) |
| 5덱 1건 | 벽시계 5.1초 (워커 3개 병렬) |
| 워커 자원 | 코어 100%씩, RSS 107MB씩 — **메모리는 문제 아님, CPU만 병목** |
| 틱 | dt = 1/60초 → 180초 = 10,800틱 × 5명 = 54,000 캐릭터-틱 |
| 함수 호출 | 덱 하나에 **2,236만 번** |

### 프로파일 (cProfile, tottime 순)

```
15,831,055  2.58s  dict.get

   455,154  0.74s  buff_manager._get_value

```

읽는 법: `get_buffs`가 캐릭터-틱당 약 2번 불린다. 대부분은 **쏘지도 않는 틱**에 «지금 최대
장탄이 몇 발인가»(`_full_ammo`)·«차지 시간이 얼마인가»(`_effective_charge_time`)를 묻느라
버프 합산을 통째로 다시 하는 것이다. 합산 결과 자체는 버프가 걸리거나 풀리지 않는 한
틱이 지나도 같다.

### 이미 들어 있는 최적화 (`buff_manager.py`)
- `_plan_cache`: (caster, target, exclude)별로 «어느 버프를 어떤 순서로 볼지» 계획을 만들어 두고,
  **시간 불변** 버프는 기여를 미리 접는다(`_PLAN_ADD/_CRIT/_QUANT/_FLAG`).
- `_buffs_cache`: 키가 `(caster, t, _cache_version, exclude)` — **t가 키에 있어서** 다음 틱은
  반드시 미스다. 같은 틱 안의 중복 호출만 잡는다.
- `_cache_version`: `_active`(활성 버프 집합)가 바뀔 때 오른다. `_BUFF_AUDIT` 모드가 «버전을
  안 올리고 `_active`를 바꾼 경로»를 잡아 준다.

### 해 본 것 — PyPy
결과는 골든 스냅샷 30/30 동일. 속도는 예열 후 **12~18%**, 첫 실행은 1.6배 느림. 우분투
패키지(3.9, 7.3.15) 기준이고 인터프리터를 둘로 나누는 비용(본체는 OCR·sqlite 때문에
CPython 유지, 워커만 PyPy + IPC)을 감당할 이득이 아니다. **채택 안 함.**

## 2. 후보 (효과 큰 순)

### A. 틱을 넘어 살아남는 `get_buffs` 캐시 — 기대 1.7~2.2×
`_buffs_cache`의 키에서 `t`를 빼고, 대신 결과에 **유효 기한**을 붙인다.

- 계산할 때 live 항목들을 훑으며 `valid_until = min(ab.expires_at)`를 구한다.
- 다음 조회가 `같은 _cache_version` 이고 `t < valid_until` 이면 그대로 돌려준다.
- 단, 계획에 **틱마다 값이 변할 수 있는 항목**이 하나라도 있으면 캐시하지 않는다(지금처럼 매번 계산):
  - `ab.has_runtime_conditions` (체력 비율·탄 수 등 조건부)
  - `per_char_stacks`·스택 수가 `_cache_version`을 올리지 않고 변하는 경우 — **확인 필요**
  - `_get_value`가 t나 수령자 상태(ATK 등)에 의존하는 caster_based 환산 — 값이 «걸린 순간»에
    고정되는지, 매 틱 재평가인지 코드로 확인해야 한다.
- 안전장치: `_BUFF_AUDIT` 모드에서는 캐시 히트 때도 정식 계산을 한 번 더 해 **결과가 다르면
  AssertionError** — 스냅샷·랜덤 대조를 이 모드로 돌려 «캐시가 틀리는 경로»를 개발 중에 잡는다.

왜 이게 제일 큰가: `get_buffs` 5.87s 중 히트로 바뀌는 비율이 높다. 버프가 붙고 떨어지는
순간은 전투 180초에 수백 번이지만 조회는 10만 번이다.

### B. `_full_ammo`·`_effective_charge_time`를 «필요할 때만» — 기대 1.3~1.5× (A와 겹침)
최대 장탄은 재장전을 시작할 때와 버프 버전이 바뀔 때만 다시 필요하고, 차지 시간은 차지를
시작할 때만 필요하다. 호출 자리를 옮기면 `get_buffs` 호출 수 자체가 준다. A가 들어가면 이득이
대부분 흡수되므로 A 뒤에 재측정해서 결정.

### C. 계획의 상수 부분 미리 접기 — 기대 1.1~1.15×
`get_buffs`는 부를 때마다 `buffs = dict(_BUFFS_ZERO)`로 시작해 `_PLAN_ADD` 항목을 루프로
더한다(1,580만 번의 dict.get 대부분이 여기). 계획을 만들 때 ADD/CRIT/QUANT/FLAG를 접은
**기본 dict 하나**를 같이 저장하고, 호출 때는 `dict(base)` 복사 + live 항목만 더한다.
결과 순서가 바뀌지 않도록 «접은 값»은 지금과 같은 순서로 더해 만든다(부동소수점 합산 순서).

### D. 안 되는 것 / 안 할 것
- **틱 해상도 낮추기** — 결과가 달라진다. 제외.
- **워커 늘리기** — 서버에 다른 것도 돌아서 제외(사용자 결정).
- **numpy 벡터화** — 틱 루프가 상태 기계라 벡터화 대상이 아니다.
- **서버 결과 캐시** — 프로필이 사람마다 달라 교차 히트가 없다. 클라이언트 캐시는 이미 있다.

## 3. 기대치 합계
A + C만으로 덱 하나 2.8초 → **1.3~1.6초** 근처. 5덱 1건은 5초 → 2.5초 안팎. B는 A 뒤 재측정.

## 4. 위험
- 캐시가 낡은 값을 주는 경우가 **조용히** 틀린다(에러가 아니라 딜이 조금 다름). 그래서 §5가 전부다.
- 부동소수점 합산 순서가 바뀌면 마지막 자리가 달라져 스냅샷이 깨진다 — 순서 보존이 설계 조건.
- 조건부 버프(체력 비율·탄 수·스택)는 캐시 대상에서 **빼는 쪽으로** 보수적으로 간다. 빠르기보다
  같음이 먼저다.

## 5. 검증 (전부 통과해야 적용)
1. `python -m context.snapshot` **30/30 통과**, 총딜이 골든과 **마지막 자리까지 동일**.
2. `_BUFF_AUDIT=1`로 같은 스냅샷을 돌려 캐시 히트 경로에서 AssertionError 0건.
3. **랜덤 대조**: 파싱된 니케에서 5인 덱 300개를 무작위로 뽑고, 약점 코드·전투 시간(60/120/180)·
   컨트롤(톡톡이·홀드·장전컨) 조합을 섞어 **옛 엔진 vs 새 엔진**의 `squad_total`·`char_total`·
   히트 목록(시각·값)을 통째로 비교 — 한 건이라도 다르면 실패. 결과 파일을 `context/baseline/`
   옆에 남긴다.
4. 유니온 레벨 오버라이드·큐브·소장품 등 프로필 층이 있는 실제 스펙으로도 3을 반복(스펙 파일은
   저장소에 안 올린다).
5. 속도: 위 프로파일 스크립트로 같은 덱을 재서 before/after를 이 문서에 적는다.
