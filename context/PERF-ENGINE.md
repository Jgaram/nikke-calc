# 계산 엔진 가속 검토안 (2026-08-25, 미적용)

상용 서버에서 덱 하나(180초 전투)에 **약 3초**가 든다. 이 문서는 «어디서 시간이 가고,
무엇을 고치면 얼마나 빨라질 수 있으며, 어떻게 결과가 같음을 증명할지»를 적어 둔 검토안이다.
**아무것도 적용하지 않았다.** 적용은 §5의 검증을 전부 통과한 뒤에만 한다.

## 1. 측정한 것

| 항목 | 값 |
|---|---|
| 서버 | Oracle A1.Flex 4 OCPU(ARM Neoverse-N1)·24GB·GPU 없음 |
| 덱 하나 | CPython 3.12: **1.8~3.0초**(고정 스펙), 실제 프로필 평균 **3.3초** (17분간 290덱 누적) |
| 5덱 1건 | 벽시계 5.1초 (워커 3개 병렬) |
| 워커 자원 | 코어 100%씩, RSS 107MB씩 — **메모리는 문제 아님, CPU만 병목** |
| 틱 | dt = 1/60초 → 180초 = 10,800틱 × 5명 = 54,000 캐릭터-틱 |
| 함수 호출 | 덱 하나에 **2,236만 번** |

### 프로파일 (cProfile, tottime 순)

```
15,831,055  2.58s  dict.get

   455,154  0.74s  buff_manager._get_value
```

읽는 법: `get_buffs`가 캐릭터-틱당 약 2번 불린다. 대부분은 **쏘지도 않는 틱**에 «지금 최대
장탄이 몇 발인가»(`_full_ammo`)·«차지 시간이 얼마인가»(`_effective_charge_time`)를 묻느라
버프 합산을 통째로 다시 하는 것이다. 합산 결과 자체는 버프가 걸리거나 풀리지 않는 한
틱이 지나도 같다.

### 이미 들어 있는 최적화 (`buff_manager.py`)
- `_plan_cache`: (caster, target, exclude)별로 «어느 버프를 어떤 순서로 볼지» 계획을 만들어 두고,
  **시간 불변** 버프는 기여를 미리 접는다(`_PLAN_ADD/_CRIT/_QUANT/_FLAG`).
- `_buffs_cache`: 키가 `(caster, t, _cache_version, exclude)` — **t가 키에 있어서** 다음 틱은
  반드시 미스다. 같은 틱 안의 중복 호출만 잡는다.
- `_cache_version`: `_active`(활성 버프 집합)가 바뀔 때 오른다. `_BUFF_AUDIT` 모드가 «버전을
  안 올리고 `_active`를 바꾼 경로»를 잡아 준다.

### 해 본 것 — PyPy
결과는 골든 스냅샷 30/30 동일. 속도는 예열 후 **12~18%**, 첫 실행은 1.6배 느림. 우분투
패키지(3.9, 7.3.15) 기준이고 인터프리터를 둘로 나누는 비용(본체는 OCR·sqlite 때문에
CPython 유지, 워커만 PyPy + IPC)을 감당할 이득이 아니다. **채택 안 함.**

## 2. 후보 (효과 큰 순)

### A. 틱을 넘어 살아남는 `get_buffs` 캐시 — 기대 1.7~2.2×
`_buffs_cache`의 키에서 `t`를 빼고, 대신 결과에 **유효 기한**을 붙인다.

- 계산할 때 live 항목들을 훑으며 `valid_until = min(ab.expires_at)`를 구한다.
- 다음 조회가 `같은 _cache_version` 이고 `t < valid_until` 이면 그대로 돌려준다.
- 단, 계획에 **틱마다 값이 변할 수 있는 항목**이 하나라도 있으면 캐시하지 않는다(지금처럼 매번 계산):
  - `ab.has_runtime_conditions` (체력 비율·탄 수 등 조건부)
  - `per_char_stacks`·스택 수가 `_cache_version`을 올리지 않고 변하는 경우 — **확인 필요**
  - `_get_value`가 t나 수령자 상태(ATK 등)에 의존하는 caster_based 환산 — 값이 «걸린 순간»에
    고정되는지, 매 틱 재평가인지 코드로 확인해야 한다.
- 안전장치: `_BUFF_AUDIT` 모드에서는 캐시 히트 때도 정식 계산을 한 번 더 해 **결과가 다르면
  AssertionError** — 스냅샷·랜덤 대조를 이 모드로 돌려 «캐시가 틀리는 경로»를 개발 중에 잡는다.

왜 이게 제일 큰가: `get_buffs` 5.87s 중 히트로 바뀌는 비율이 높다. 버프가 붙고 떨어지는
순간은 전투 180초에 수백 번이지만 조회는 10만 번이다.

### B. `_full_ammo`·`_effective_charge_time`를 «필요할 때만» — 기대 1.3~1.5× (A와 겹침)
최대 장탄은 재장전을 시작할 때와 버프 버전이 바뀔 때만 다시 필요하고, 차지 시간은 차지를
시작할 때만 필요하다. 호출 자리를 옮기면 `get_buffs` 호출 수 자체가 준다. A가 들어가면 이득이
대부분 흡수되므로 A 뒤에 재측정해서 결정.

### C. 계획의 상수 부분 미리 접기 — 기대 1.1~1.15×
`get_buffs`는 부를 때마다 `buffs = dict(_BUFFS_ZERO)`로 시작해 `_PLAN_ADD` 항목을 루프로
더한다(1,580만 번의 dict.get 대부분이 여기). 계획을 만들 때 ADD/CRIT/QUANT/FLAG를 접은
**기본 dict 하나**를 같이 저장하고, 호출 때는 `dict(base)` 복사 + live 항목만 더한다.
결과 순서가 바뀌지 않도록 «접은 값»은 지금과 같은 순서로 더해 만든다(부동소수점 합산 순서).

### D. 안 되는 것 / 안 할 것
- **틱 해상도 낮추기** — 결과가 달라진다. 제외.
- **워커 늘리기** — 서버에 다른 것도 돌아서 제외(사용자 결정).
- **numpy 벡터화** — 틱 루프가 상태 기계라 벡터화 대상이 아니다.
- **서버 결과 캐시** — 프로필이 사람마다 달라 교차 히트가 없다. 클라이언트 캐시는 이미 있다.

## 3. 기대치 합계
A + C만으로 덱 하나 2.8초 → **1.3~1.6초** 근처. 5덱 1건은 5초 → 2.5초 안팎. B는 A 뒤 재측정.

## 4. 위험
- 캐시가 낡은 값을 주는 경우가 **조용히** 틀린다(에러가 아니라 딜이 조금 다름). 그래서 §5가 전부다.
- 부동소수점 합산 순서가 바뀌면 마지막 자리가 달라져 스냅샷이 깨진다 — 순서 보존이 설계 조건.
- 조건부 버프(체력 비율·탄 수·스택)는 캐시 대상에서 **빼는 쪽으로** 보수적으로 간다. 빠르기보다
  같음이 먼저다.

## 5. 검증 (전부 통과해야 적용)
1. `python -m context.snapshot` **30/30 통과**, 총딜이 골든과 **마지막 자리까지 동일**.
2. `_BUFF_AUDIT=1`로 같은 스냅샷을 돌려 캐시 히트 경로에서 AssertionError 0건.
3. **랜덤 대조**: 파싱된 니케에서 5인 덱 300개를 무작위로 뽑고, 약점 코드·전투 시간(60/120/180)·
   컨트롤(톡톡이·홀드·장전컨) 조합을 섞어 **옛 엔진 vs 새 엔진**의 `squad_total`·`char_total`·
   히트 목록(시각·값)을 통째로 비교 — 한 건이라도 다르면 실패. 결과 파일을 `context/baseline/`
   옆에 남긴다.
4. 유니온 레벨 오버라이드·큐브·소장품 등 프로필 층이 있는 실제 스펙으로도 3을 반복(스펙 파일은
   저장소에 안 올린다).
5. 속도: 위 프로파일 스크립트로 같은 덱을 재서 before/after를 이 문서에 적는다.

### 정정
- **후보 C는 무효.** 상수 버프를 미리 접어 두면 live 항목과의 **부동소수점 합산 순서**가 바뀐다.
  코드 주석(`_build_plan`)이 이미 같은 이유로 금지하고 있다. 지운다.
- **후보 A(만료 시각만 보는 캐시)도 사실상 무효.** 거의 모든 계획에 체력·풀버스트·차지 같은
  **런타임 조건 버프**가 섞여 있어 «만료 전이면 재사용»이 성립하는 조회가 0~3%다.
- 이미 조회의 37~56%가 같은 틱 캐시 히트다. 비싼 건 나머지 절반이다.
- 버전 갱신이 **5~6틱마다** 한 번이다(버프가 붙고 떨어짐). 그때마다 계획을 캐릭터·대상별로
  전부 다시 짠다 — `_build_plan`이 덱 시간의 **14%**.

### 남는 후보 (기대치를 낮춰서)
- **E. 계획의 증분 갱신** — 버프 하나가 붙거나 떨어질 때 계획 전체를 다시 짜지 않고, 그 항목
  하나를 `_active` 순서상 제자리에 끼우거나 뺀다. 순서 보존이 그대로라 결과가 같아야 한다.
  기대 **~1.1~1.15×** (14%의 대부분).
- **F. 검증형 틱 간 캐시** — 결과와 함께 live 항목들의 «서명»(만료 여부·조건 판정 결과·스택·
  잔탄·체력%·참조 스택)을 저장하고, 다음 조회 때 서명만 다시 계산해 같으면 재사용한다.
  조건 판정은 건당 ~9µs로 싸다(전체 조회 56µs). 무효화가 5~6틱마다라 재사용 창이 짧다.
  기대 **~1.2×**, 구현·검증 비용은 제일 크다.
- E + F 합쳐도 **1.3~1.4×** — 5덱 5초 → 3.7초. 1차 안의 «2×»는 틀렸다.

### 로직을 안 바꾸는 가속 (같은 소스를 그대로 컴파일)
- **Cython/mypyc/Nuitka로 `buff_manager.py`·`timeline.py`를 그대로 컴파일** — 파이썬 의미가
  그대로라 결과가 같아야 하고(부동소수점 연산도 같은 IEEE 배정도), 이런 코드에서 보통
  1.2~1.6×(Cython, 무주석), mypyc는 타입이 맞으면 2~4×. 서버에 gcc·python3-dev·컴파일러
  패키지가 필요하다 — **상용에 빌드 도구를 깔아야 해서 허락 뒤에** /tmp 복사본으로 잰다.
  로컬(Windows)에는 C 컴파일러가 PATH에 없다.

### 지금 상태
- `feat/engine-buff-cache` 브랜치는 만들어만 두었고 **코드 변경은 없다.**
- 두 엔진 병행 대조 하네스(히트 시각·값·버스트 사이클까지 완전 일치)는 어느 후보를 하든
  먼저 만든다 — §5 그대로.

## 8. 러스트 트랙 (검토용 개요)

전제: 기여자는 코드를 쓰지 않는다 — 데이터·영상을 주고 코딩은 AI가 한다. 그래서 «러스트는
기여 문턱이 높다»는 이유는 사라지고, 남는 조건은 하나다: **파이썬 엔진과 마지막 자리까지 같은가**.

목표는 속도가 아니라 배치다: 같은 코어가 서버(PyO3 또는 단독 바이너리)와 **브라우저(WASM,
수백 KB, 0.1~0.3초)** 에서 돌아, 서버 계산 부하가 사라진다.

### 층 나누기
- 파이썬이 남는 것: 수집·파싱(`scraper/`), 육성 프로필 변환(`profile_convert`), 스펙 조립(`context/spec.py`),
  회귀 스냅샷. **데이터 층은 그대로** — 니케·스킬 추가는 지금처럼 JSON이다.
- 러스트가 맡는 것: `calculator/`(base_stat·buff_manager·timeline·damage·sim_result) — 어휘(stat 140종·
  target 66종·condition 33종)를 해석하는 상태기계.
- 입력 경계: 지금 워커가 받는 것과 같은 JSON(스쿼드 dict·config·enemy). 출력도 `SimResult`와 같은 JSON.
  경계를 JSON으로 고정해 두면 파이썬 엔진과 러스트 엔진을 **같은 입력으로 같이 돌려** 대조할 수 있다.

### 순서
1. **하네스 먼저**: 파이썬 엔진으로 랜덤 덱 300개 × (코드·시간·컨트롤) 조합의 입력 JSON과 골든
   출력(총딜·니케별·히트 목록 시각/값·버스트 사이클)을 만들어 둔다. 러스트는 이걸 맞추는 게 일이다.
2. `base_stat` → `damage` → `buff_manager` → `timeline` 순으로 옮기며 단계마다 대조. 부동소수점은
   **합산 순서를 파이썬과 똑같이** 유지(f64, 같은 연산 순서) — 그래야 마지막 자리가 같다.
3. 서버에 «참고용 두 번째 엔진»으로 붙여 실제 요청마다 둘 다 돌리고 차이를 로그로 쌓는다.
   차이 0이 충분히 오래 이어지면 러스트를 정식으로, 파이썬은 골든으로 남긴다.
4. WASM 빌드를 브라우저 «직접 계산»에 연결(Pyodide 대체).

### 새 메카닉이 생기면
파이썬 정본에 먼저 넣고(스냅샷 갱신), 러스트가 따라가며 하네스로 같음을 증명한다. 어휘 확장은
enum 가지 + match 팔 하나로 끝나게 짠다. 두 엔진을 함께 유지하는 부담이 영구히 남는 것이
이 트랙의 진짜 비용이다.

## 9. 새 세션 착수 메모 (러스트 트랙)

이 절만 읽으면 시작할 수 있게 적는다.

- **결정된 것**: 원본 저장소는 안 건드린다. 러스트 코어는 **별도 저장소**(예: `C:\claude\nikke-core`).
  파이썬 엔진이 정본·골든이고, 러스트는 «마지막 자리까지 같은» 두 번째 엔진이다. 순서는 §8 —
  **하네스 먼저**. 기여자는 코드를 안 쓰니(데이터·영상만) 러스트의 기여 문턱은 문제 아님.
- **파이썬 엔진 사본**: 이 저장소 `calculator/`·`context/spec.py`(포크 `feat/union-raid`, 원본 master보다
  재장전 지연·원클립 등 4커밋 앞섬). 원본 master 그대로는 `C:\claude\nikke-calc-perf`(빈 브랜치).
  **포크 쪽을 기준으로 맞춘다** — 사이트가 쓰는 게 그것이다.
- **경계 JSON**: 서버 `web/server.py:_sim_one`과 워커 `web/src/worker.js`의 PY 블록이 만드는
  `build_squad(names, over, profile)` → `build_config(squad, {duration, rng_mode:"expected", …})` →
  `simulate(squad, config, enemy)` 입력, 출력은 `SimResult`(`calculator/sim_result.py`, `squad_total`·
  `char_total`·히트 목록·`burst_cycles`). 러스트는 squad dict·config·enemy JSON을 받아 같은 모양으로 낸다.
- **회귀 도구**: `python -m context.snapshot`(골든 30건), `python -m context.doclint`.
  프로파일·부하 스크립트는 세션 스크래치에 있었으니 다시 쓰면 된다(덱 하나 = cProfile 한 번).
- **수치 기준**(2026-08-25): 덱 하나 CPython 2.8~3.3초, 5덱 5.1초(워커 3), 서버 A1 4코어. 목표는 러스트
  네이티브 0.05~0.15초, WASM 0.1~0.3초.
- **주의**: 부동소수점 합산 순서(`_active` 순서) 보존, `round` 은행가 반올림, dict 삽입 순서, `math.inf`
  만료, 지연 resolve(`_resolve_lazy`)의 부작용(로그·대상 확정 시점)까지 그대로. `_BUFF_AUDIT`가 파이썬
  쪽 캐시 검산 스위치다.
- **도구 설치**(rustup·cargo·wasm-pack)는 다운로드라 사용자 허락 뒤에.
