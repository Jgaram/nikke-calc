# 아르카나 동작 시나리오

> 모드: 보강 (`data/parsed_skills.json` 등록 완료)
> 작성 목적: 이미 등록된 캐릭터의 **회귀 검증**. 버그 수정·`/char-impl` Phase D 기준으로 사용.

## 기본 정보
- 버스트 단계: B2
- 본인 쿨다운: 40s (2사이클에 1회)
- 무기 유형: RL (차지형, 장탄 6, 재장전 2.5s, 풀차지 250%)
- 코드/클래스: 전격 / 지원형 / 엘리시온
- 작성 사이클 수: 2 (본인 사용 사이클 + 미사용 사이클)

## 핵심 전제 — "이사벨 전용 설계"

아르카나의 주력 버프는 전부 **`full_burst_end` 시점에 자신이 `운명의 수레바퀴 카드` 상태일 것**을 요구한다.
그런데 카드는 자신의 `burst_cast`(B2 발동) 시점부터 **10초**만 유지된다.

```
t_c          아르카나 B2 발동 → 운명의 수레바퀴 카드 (t_c ~ t_c+10)
t_c + 0.15   풀버스트 시작       (burst_switch_delay 0.1 + 진입 0.05)
t_c + 10.15  풀버스트 종료       (기본 10초)   ← 카드는 t_c+10 에 이미 만료
```

즉 **기본 10초 풀버스트에서는 카드가 0.15초 차이로 먼저 꺼져 조건부 버프가 전부 불발**한다.
이사벨의 `소닉 체이서 5`(`fullburst_duration -5s`)가 들어가야만

```
t_c + 5.15   풀버스트 종료 → 카드 잔여 4.85초 → 조건 성립
```

가 되어 버프가 켜진다. 로스터 전체에서 `fullburst_duration`이 **음수**인 캐릭터는 이사벨뿐이다
(소다 : 트윙클링 바니는 +2/+3초로 반대 방향).

`parsed_skills.json`의 `target: "이사벨"` 하드코딩(원문은 `직전에 버스트 스킬을 사용한 기본 버스트 단계가
Step 3인 전격 코드 아군 전체`)은 이 구조 때문에 **의도된 고정**이다. 근거·재검토 트리거는
`PARSING-CHARS.md` 아르카나 항목 참조. → 범용 target으로 일반화 금지.

## 스킬 간 상호작용

- **조건부 버프 5종의 값은 `운명의 수레바퀴 카드` 생존 여부에 종속**
  - 경로: 스킬3 `burst_cast` → 카드(10s) → `full_burst_end` 시점 `self_state` 판정 → 스킬1/2 조건부 5종
  - 시점: `full_burst_end` 프레임에 카드가 살아 있어야 함. 여유는 **이사벨의 −5초에서만** 나온다.
  - 위험: `burst_switch_delay`(0.1) / 풀버스트 진입 딜레이(0.05) / `fullburst_duration` 집계 로직 중
    하나라도 바뀌면 네거티브 케이스가 **0.15초 마진**에서 뒤집힌다. 값 변경 시 네거티브 스쿼드 재검증 필수.

- **`full_burst_end`의 실행 순서 의존** — `timeline.tick()`은 `bm.notify("full_burst_end")`를 전원에게
  돌린 **뒤에** `state["burst_casted"]`를 리셋한다. 순서가 뒤집히면 `burst_casted` 조건이 깨져
  마법사 카드/마법사 카드 2/힘 카드가 통째로 사라진다.

- **`fullburst_duration`의 caster 귀속** — `burst_cast` 타이밍으로 등록된 `fullburst_duration`은
  `ab.caster == self._fb_caster`(이번 사이클 3단계 발동자)일 때만 합산된다. 이사벨의 −5초 버프는
  `duration: null`(영구)이라 이 게이트가 없으면 신데렐라 사이클에도 5초 풀버스트가 되어
  아르카나 버프가 잘못 켜진다. → B사이클 풀버스트 길이 10초 확인이 이 게이트의 회귀 지표.

- **마법사 카드 → 이사벨 페더 이젝션** — `skill_cooldown_pct −75%`가 `every:15.0s`를
  3.75s로 줄인다. `buff_manager` `every:Ns` 블록에서 처리. (⚠️ 아래 유저 확인 사항 Q2)

## 유저 확인 사항

- Q1: `target: "이사벨"` 하드코딩이 파싱 실수인가?
  - A: **아니다. 의도된 고정.** 이사벨은 풀버스트 시간을 5초 줄이는 유일한 캐릭터이고,
    아르카나의 조건부 버프는 그 단축이 있어야만 `full_burst_end`까지 카드가 남는다.
    게임 맥락상 아르카나는 이사벨 전용 설계 캐릭터 — 범용 서포터가 아니다. (유저 판단, 2026-07-30)
    → 재검토 트리거: **`fullburst_duration`이 음수인 캐릭터가 새로 추가될 때**.

- Q2: 이사벨 `페더 이젝션`(`every:15s`)에 `마법사 카드 −75%`가 걸릴 때, 이미 진행 중인 쿨타임도
  같이 줄어드는가? → **현재 구현은 줄이지 않는다.** 아래 "발견된 이슈" 참조. *(미해결 — 유저 답변 대기)*

### BUG-1 (치명) — 유한 duration 버프가 트리거 조건 소멸과 함께 조기 종료 ✅ 해소

**해소** (2026-07-30) — `_has_runtime_cond()`에 `expires`를 넘겨, **유한 duration 버프는
런타임 재평가 대상에서 제외**한다. 재평가는 `duration: -1`/`null`에만 적용 — 조건부 passive
블록이 이미 쓰던 `expires_at < inf → continue`와 같은 기준이다. 아래 예측치가 그대로 재현됐고
10스쿼드가 전부 상승했다. 히트 수는 전 스쿼드 불변(딜만 변동).


`buff_manager._RUNTIME_COND_PREFIXES`에 `self_state:`가 포함돼 있어, 이 조건이 붙은 버프는
**`get_buffs()` 조회 때마다 조건이 재평가**된다(`ActiveBuff.has_runtime_conditions`).
아르카나의 조건은 `운명의 수레바퀴 카드`이고 카드는 10초짜리라, `full_burst_end`(카드 시작 +5.15s)에
부여된 15초 버프가 **카드 만료와 동시에 죽는다**.

실측 (표준 스쿼드, 이사벨 기준):

```
t=13.0  atk_dmg_pct = 267.74   atk_flat = 348,579.2   ← 마법사 카드 2(+180) · 힘 카드(+197,719) 살아 있음
t=13.2  atk_dmg_pct =  77.74   atk_flat =  95,938.0   ← 카드 만료(13.10) → 둘 다 소멸
                                                        (버프 자체 만료는 23.25인데 10초 일찍 꺼짐)
```

지속 15.0s → **실효 4.85s (32%)**. 영향 범위:

| 스쿼드 | 현재 총딜 | 조건을 발동 게이트로만 처리 시 | 차이 |
|---|---|---|---|
| 스쿼드5 (아니스 : 스타·아르카나·이사벨·신데렐라·크라운) | 3,713,887,739 | 4,178,733,647 | **+12.52%** |
| └ 이사벨 단독 | 867,228,965 | 1,329,495,944 | **+53.30%** |
| 실전 (토브·아르카나·이사벨·드레이크·도라) | 1,176,205,073 | 1,500,876,856 | **+27.60%** |
| └ 이사벨 단독 | 575,711,988 | 899,806,886 | **+56.29%** |

**원문 근거 — 조건은 발동 시점 게이트다.**
`■ 풀 버스트 타임 종료 시 자신이 운명의 수레바퀴 카드 상태라면 ... [15초 유지]`
`~시`(트리거) + `~라면`(그 시점 조건) + `[N초 유지]`(버프 자체 지속)의 3단 구조.

**일반 규칙 후보**: 이 문법은 아르카나 전용이 아니다. 같은 구조를 확인한 예 —

| 캐릭터 | 원문 | 현재 처리 |
|---|---|---|
| 루주 | `자신이 소드 코인 상태라면 아군 전체에게 [...] [10초 유지]` | 코인 소멸 시 조기 종료 |
| 브래디 | `풀 차지 공격 명중 시 자신이 나누고 싶은 맛 상태라면 [...] [5초 유지]` | 〃 |
| 벨벳 | `풀 차지 공격 시 풀 버스트 타임일 때 한하여 [...] [3초 유지]` | 풀버스트 종료 시 조기 종료 |
| 퀀시 : 이스케이프 퀸 | `루트 탐색 1단계 최대 중첩 상태라면 [...] [1초 유지]` | 스택 하락 시 조기 종료 |
| 네온 : 비전 아이 | `자신이 건강한 몸 상태가 아니라면 [...] [3초 유지]` | 〃 |

→ **`duration`이 유한 양수인 buff는 condition을 발동 시점에만 평가**하고,
런타임 재평가는 `duration: -1`/`null`(지속·영구)인 buff에만 적용하는 것이 원문 문법과 일치한다.

**실제 수정 범위**: runtime condition 보유 191건 중 **유한 duration 73건 / 24명**
(아르카나 4건 포함). 나머지 118건(지속·영구)은 동작 불변. 유저 승인 후 전면 수정.

원문 대조로 게이트 해석을 확증했다 — 특히 스노우 화이트는 "지속 시간 중 **발동 시**"로
원문에 못박혀 있고, 스노우 화이트 : 헤비암즈는 `[받는 대미지 ▲] [4초 유지]`가
`during_charge` 조건이라 **차징이 끝나는 순간, 즉 풀차지 탄이 꽂히는 바로 그 시점에
증발**하고 있었다 (인게임 확인 완료, 2026-07-30 유저).

### BUG-2 (중) — `skill_cooldown_pct`가 진행 중인 쿨타임에는 적용되지 않는다 (위상 밀림) ✅ 해소

**해소** (2026-07-30) — `_next_fire`를 `(next_t, interval)` 튜플로 바꿔 interval 변화를
감지하고, 남은 시간을 새 배율로 **비례 재조정**한다. `tick()`에 dt가 없어 아래의
"잔여 진행률 차감"은 못 쓰지만, 비례 스케일이면 dt 없이 쿨감이 켜질 때·꺼질 때
양방향으로 정확하다. 발동 17 → **27회**, 이사벨 딜 +4.29%.


`buff_manager.py`의 `every:Ns` 처리는 다음 발동 시각을 `self._next_fire[eid] += interval` 로
**발동 순간에만** 갱신한다. 따라서 버프가 켜져도 **이미 예약된 다음 발동 시각은 그대로**고,
그 예약이 버프 창 밖이면 창 전체를 흘려보낸다.

180초 시뮬(`토브,아르카나,이사벨,드레이크,도라`, seed=1) 실측 — 마법사 카드 창은 6회(각 15초):

```
페더 이젝션 발동: 15.000 18.750 22.500 26.267 41.267 56.267 60.017 75.017
                 90.017 93.767 108.767 123.767 127.517 142.500 157.500 161.250 176.250
마법사 카드 창:   [8.25~23.25] [42.25~57.25] [76.25~91.25] [110.25~125.25] [144.25~159.25] [178.25~]
```

- 1번째 창: 위상이 맞아 3회 가속 발동
- 2~5번째 창: 각 **1회씩만** — 직전 발동이 창 밖이라 15초 예약이 창을 건너뛴다
- 총 17회. 인게임 기대치(창 안 3.75s 주기 = 창당 약 4회)는 **약 30회**

**남은 과제**: 수정 후 27회로 기대치에 3회쯤 못 미친다. 이 스쿼드의 도라가
`parsed_skills.json` 미등록이라 딜 비교용으로 부적합하다 — **도라 등록 후 재확인**한다
(유저 결정, 2026-07-30. 지금은 진행하지 않음).

영향: `페더 이젝션`은 이사벨 딜의 약 3~5% → 이사벨 딜 **약 2~3% 과소평가**.
`IMPL-STATUS.md`는 `skill_cooldown_pct`를 ⚠️(`target_effect` 미지원)로만 적어 두었고
이 위상 문제는 미기재.

수정 방향(제안): `_next_fire`를 절대 시각이 아니라 **잔여 쿨타임 진행률**로 관리 —
매 프레임 `remaining -= dt / (1 + cool_pct/100)` 형태로 감소시키면 버프가 켜지는 즉시
남은 쿨도 같은 비율로 줄어든다.

### BUG-4 (중) — 대기 중 도착한 `burst_cooldown_reduce`가 예약된 버스트 시각을 앞당기지 않는다 ✅ 해소

**해소** (2026-07-30) — `_next_action_t`가 **의도된 딜레이**(전환 0.1s / reenter 0.5s /
진입 0.05s)와 **쿨 대기 예측**을 섞어 쓰던 것이 원인이었다. `_cd_wait_candidates`
(쿨 대기일 때만 채워지는 후보 목록)로 둘을 구분하고, 그 목록이 있을 때만 `tick()`에서
`_next_action_t`를 앞당긴다. 성공 캐스트 시 `_try_use_stage` 진입부의 초기화로 자동으로
꺼지므로 전환 딜레이 구간을 건드리지 않는다 — 아래 ⚠️의 붕괴가 재현되지 않음을
단계 타임라인(0.1/0.1/0.05 전 사이클 유지)으로 확인했다.
`레이드_루주` +3.6%, 13사이클 중 2사이클이 13.0 → 12.25로 당겨졌다.


`BurstController._try_use_stage()`의 대기 분기:

```python
earliest = min(self.burst_ready_at.get(n, 0.0) for n in candidates)
self._next_action_t = max(self._next_action_t, earliest)   # timeline.py:993
```

`_next_action_t`가 한 번 잡히면 `tick()`은 `t >= _next_action_t`가 되기 전까지 해당 단계를
재평가하지 않는다. 그 사이에 버쿨감이 들어와 후보가 이미 발동 가능해져도 **예약된 시각까지 그대로 대기**한다.

실측 (`루주·아르카나·이사벨·트리나·라플라스 : 얼티밋 히어로`, 버충 4초):

```
t=36.750  stage1 대기 → _next_action_t = 41.500   (루주 ready 41.5)
t=38.083  루주 카드 스로우 −7s → 루주 ready 38.083 로 앞당겨짐
t=41.500  stage1 발동                              ← 3.42초 헛대기
```

수정 방향: 대기 사유가 **쿨타임**일 때만(= `burst_switch_delay`로 잡힌 `_next_action_t`는 제외)
매 tick 후보 최소 `burst_ready_at`으로 `_next_action_t`를 다시 내린다.
`_try_use_stage`의 대기 분기에서 플래그를 세우고 `tick()` 진입부에서 재계산하는 형태.

⚠️ 단순히 "phase가 `stage:N`이면 항상 재계산"으로 구현하면 **단계 전환 딜레이 0.1초까지 무시**되어
풀버스트 진입이 0.25s → 0.083s로 붕괴한다. 반드시 쿨 대기 상태에만 적용할 것.

**발동 조건**: 버쿨감이 부족해 stage 대기가 실제로 발생하는 스쿼드에서만 나타난다.
쿨이 넉넉하면 대기 자체가 없어 이 경로를 타지 않는다(아래 사이클 검증에서 장탄 200% 케이스는
현재 코드와 수정본의 결과가 완전히 동일했다).
