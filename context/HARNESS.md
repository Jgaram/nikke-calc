# 회귀 하네스

계산기를 고친 뒤 **기존 캐릭터가 조용히 틀어졌는지** 잡는 도구.

```bash
python -m context.snapshot                  # 전체 비교
python -m context.snapshot --squad 스쿼드1   # 일부만
python -m context.snapshot --list           # 스쿼드 목록
python -m context.snapshot --update         # baseline 갱신 (유저 확인 후에만)
```

전체 20스쿼드 약 80초. FAIL 시 exit code 1.

### 캐릭터 스펙 (`snapshot.py` 기본값)

총딜 수치를 해석하려면 어떤 스펙으로 돌린 것인지 알아야 한다. 스쿼드 dict는
이름만 주고 나머지는 `timeline.DEFAULT_CHAR`가 채운다 (`equip_skills`만 비운다).

| 항목 | 값 |
|---|---|
| 레벨 | 400 |
| 돌파 | 3 |
| 코어 강화 | 0 |
| 친밀도 | 30 |
| 스킬 레벨 | 10 |
| 버스트 리젠 시간 | 2.0s |
| 장비 등급 | 전 부위 T5 (옵션 없음) |
| 장비 옵션 합산 | atk_pct 20%, max_ammo_pct 120% |
| 큐브 | 재장 Lv.15 |
| 콘솔 | 공용 180 / 클래스 100 / 회사 100 |
| 컬렉션 단계 | SR15 |

즉 **하네스 총딜은 실전 기대딜이 아니다.** 스펙이 고정된 비교용 수치일 뿐이다.

---

## 이 도구가 하는 일과 하지 않는 일

**한다** — 변화 감지. "무엇이 이전과 달라졌는가"를 캐릭터·효과 단위로 짚는다.

**하지 않는다** — 정확성 검증. baseline을 찍는 순간 그 시점 코드의 **기존 버그도 "정상"으로 고정**된다.
정확성은 `context/scenarios/<이름>.md`의 검증 체크리스트가 담당한다.

즉 하네스가 PASS라고 해서 계산이 맞다는 뜻이 아니다. "내가 방금 고친 것 때문에
다른 게 바뀌지는 않았다"는 뜻이다.

---

## 왜 결정론적인가

`simulate(..., seed=N)`을 주면 크리 판정·코어히트·`prob:N` 조건·`allies_random`이
모두 재현되어 결과가 완전히 같아진다. 프로세스가 달라도, `PYTHONHASHSEED`가 달라도 같다.

그래서 **오차 범위가 없다. 완전 일치해야 PASS다.**

> 참고 — `simulate()`의 `seed` 기본값은 `None`(시드 미고정)이다.
> UI의 기대딜은 여러 회 평균이 맞으므로 앱은 지금도 매번 다른 값을 낸다.
> 시드는 하네스와 `context/sim.py`만 명시적으로 넘긴다.

## 스냅샷 4층 구조 — diff 읽는 법

절대 시각은 저장하지 않는다. 발사 타이밍이 1프레임(0.0167s) 밀리는 건 노이즈지만,
**"버프가 적용된 다음에 대미지가 계산되는가" 하는 순서는 신호**이기 때문이다.

### L1 수치 — 무엇이 얼마나
캐릭터별 총딜, 스킬별 딜·히트수, `hit_tag` 분포, 크리 수, 풀버스트 횟수.

```
[L1 수치]
스쿼드 총딜  1,862,282,550 → 1,863,145,587  (+863,037, +0.05%)
[라피 : 레드 후드] 스킬 <부착형 유탄 4>  딜 225,995,644 → 226,031,557  히트 106 → 106
```
→ **L1만 움직였다면** 순수한 계수·수치 변경이다. 발동 타이밍은 그대로.

### L2 발동 횟수 — 몇 번 걸렸나
버프/인스턴트 이름별 발동 횟수와 대상 집합.

```
[L2 발동 횟수]
! 버프 [붉은 두건] 발동 12 → 9회
+ 버프 [○○] 신규 발동 4회 → ['미하라']
- 버프 [××] 발동 사라짐 (기존 30회)
```
→ **가장 먼저 볼 층.** 버프가 안 걸리게 된 회귀는 여기서 바로 드러난다.
딜이 상쇄되어 L1이 조용해도 L2는 반응한다.

### L3 순서 — 무엇 다음에 무엇이
풀버스트 진입을 경계로 사이클을 나누고, 각 사이클 안의 이벤트를 **시각 없이 순서열로** 기록.
히트는 이벤트 사이 구간의 집계로 압축한다.

```
[L3 순서]
── 사이클 1 순서 변화 ──
   B+ 릴렉스 → 크라운
  -HITS 라피 : 레드 후드:1 crit:0 core:0
  +HITS 라피 : 레드 후드:3 crit:0 core:0
   B- 터진 거품 2 → __enemy__
```
표기: `B+` 버프 활성 / `B-` 버프 만료 / `I` 인스턴트 / `BURST` 버스트 이벤트 / `HITS` 구간 히트 집계.

→ **버프와 히트의 상대 순서**가 바뀌면 여기서 잡힌다. 1프레임 밀림은 diff를 만들지 않지만,
버프가 히트보다 뒤로 밀리면 즉시 드러난다.

### L4 위상 — 정수 지표
사이클 간격(0.05초 정밀도)과 "버프 발동 → 대상의 다음 히트까지 프레임 수" 분포.

```
[L4 위상]
사이클 간격  [12.55, 12.55, ...] → [12.55, 17.30, ...]
버프 [○○] 발동→다음히트  3프레임 11→8, 4프레임 22→25
```
→ 사이클 간격이 12.5초에서 크게 벗어나면 버스트 사이클이 깨진 것이다.

## baseline 갱신 규칙

`context/baseline/*.json`은 **자동 생성물이다. 손으로 편집하지 않는다.**

FAIL이 났을 때:

1. diff를 **그대로 유저에게 보고**한다. 재시도하지 않는다.
2. 유저가 "그 변화는 의도한 것"이라고 확인해준 뒤에만 `--update`.
3. 의도치 않은 변화면 회귀다 — 원인을 찾을 때까지 갱신하지 않는다.

스쿼드를 추가하려면 `context/snapshot.py`의 `SQUADS`에 항목을 넣고
`--update --squad <이름>`으로 baseline을 만든다.

## 스쿼드 커버리지

**파싱된 54명 전원을 20스쿼드가 커버한다.** (baseline 5.8MB)

| 스쿼드 | 성격 |
|--------|------|
| `스쿼드1` ~ `스쿼드5` | 초기 지그. 아르카나+이사벨 케이스는 `스쿼드5` |
| `레이드_*` (14개) | **실전 레이드 조합 기반** — enikk.app 솔로레이드 시즌 30~39, 53,150 파스에서 추출 |
| `지그_리타` | 리타는 9시즌 실전 조합에 한 번도 안 나와 템플릿 지그를 쓴다 |

실전 조합이 없는 캐릭터(리타처럼)는 `GAMEPLAY.md §스쿼드 구성 §표준 테스트 스쿼드`의
템플릿에 `TARGET`만 갈아끼워 만든다. 버스트 단계·쿨다운별 템플릿이 거기 있다.

`레이드_*`의 조연은 임의 지그가 아니라 **실제 상위 조합 그대로**다.
따라서 실전에서 실제로 맞물리는 버프 상호작용까지 스냅샷에 들어온다.
대신 조합을 바꾸면 baseline이 통째로 흔들리므로, **커버 대상만 보고 조연을 갈아끼우지 않는다.**

### 스쿼드를 새로 추가할 때

> **시작 전 필수** — `context/GAMEPLAY.md`의 `## 스쿼드 구성` 절을 읽는다.
> (§유효한 스쿼드의 조건 / §버스트 쿨타임 감소 / §**버스트 사용 순서와 배치** / §더미 캐릭터)

특히 다음 두 가지는 이 하네스를 만들면서 실제로 밟은 함정이다.

- **멤버 순서 = 버스트 사용 순서다.** 관찰 대상은 반드시 **자기 단계 안에서 맨 앞**에 둔다.
  뒤로 밀리면 같은 단계의 앞사람에게 선점당해 **버스트를 한 번도 못 쓴 채** 스냅샷이 찍힌다.
  초기 배치에서 소다·델타·헬름:아쿠아마린·나가·벨벳·프리카 6명이 이 상태였다.
- **레드 후드(`burst_stage: "A"`)의 단계를 고정하지 않는다.** 고정하면 라피 : 레드 후드의
  `no_burst1_ally` 조건이 깨져 라피의 1버 전환이 막힌다. 배치 순서로만 조정한다.

그 밖에:

- `test_B3`를 한 스쿼드에 두 번 넣지 않는다 (`burst_cooldown` 소급 보정 중복).
  B3 두 자리가 필요하면 한쪽은 `스노우 화이트 : 헤비암즈`.
- 버스트를 안 쓰는 캐릭터는 `config={"no_burst_char": "이름"}`. 한 명만 지정할 수 있다.
- 버스트 단계·쿨다운은 `data/parsed_nikke.json`의 `burst_stage` / `burst_cooldown`.

## 이력

### 2026-07-21 — 커버리지 43% → 100% (실전 레이드 조합 도입)

23명 → 54명. 5스쿼드 → 20스쿼드, baseline 1.3MB → 5.8MB.

조연을 템플릿 지그가 아니라 **실전 상위 조합**에서 가져왔다. enikk.app의
GraphQL 엔드포인트(`POST /api/webapp`, `SRParses(raid, characters: [])`)로
솔로레이드 시즌 30~39 **53,150 파스**를 수집하고, 계산기가 파싱한 캐릭터로만 이루어진
조합에 한정해 greedy set cover로 최소 스쿼드 수를 뽑았다.

미커버 31명 중 30명이 실전 조합을 갖고 있었다 (리타만 없어 템플릿 지그).
시즌 39 하나만 보면 15명이 안 나오지만, 10시즌으로 넓히면 거의 전원 등장한다.

편성 중 확인된 사실 — 둘 다 `GAMEPLAY.md`에 반영했다:

- **멤버 순서가 버스트 사용 우선순위다.** 첫 배치에서 소다·델타·헬름:아쿠아마린·나가·
  벨벳·프리카 6명이 같은 단계 앞사람에게 선점당해 버스트를 한 번도 쓰지 못했다.
  커버 대상인데 버스트가 안 걸리면 스냅샷의 의미가 없다. 자기 단계 맨 앞으로 옮겨 해결.
- **레드 후드의 단계를 고정하면 안 된다.** `burst_stage`를 `"1"`로 주면 라피 : 레드 후드의
  `no_burst1_ally`가 거짓이 되어 라피의 1버 전환이 막힌다.

사이클 판정 기준도 바꿨다. 기존 "12.5초에서 5초 이상 벗어나면 잘못"은 버쿨감 구성이
다른 스쿼드를 전부 오탐한다 (`레이드_소다`의 20초 균일, 볼륨·리타의 감쇠 후 정착,
아르카나+이사벨의 7.25초 교대는 모두 정상). **버쿨감 프로필별 패턴 대조**로 대체했다.

### 2026-07-21 — 하네스 도입

- `context/regression_test.py`(총딜 ±3σ, 30회 재측정 방식) 대체.
  이관 시점에 시드 고정 총딜이 기존 5스쿼드 평균 대비 전부 **1σ 이내**임을 확인했다
  (0.15σ ~ 0.98σ). 즉 기존 기준과 모순되지 않는다.
- 기존 방식이 놓치던 범위: 스쿼드1 기준 tol이 ±29,306,951이었으므로
  **0.05%(약 86만) 규모 변화는 검출 불가능**했다. 하네스는 이를 L1에서 잡는다.

### 2026-07-21 — 비결정성 버그 수정 (하네스가 발견)

`BuffManager._cond_passive_prev`가 `id(ActiveBuff)`를 키로 쓰면서, 버프 만료 시
항목을 정리하지 않았다 (`reset()`에서만 `clear()`). 만료된 ActiveBuff가 GC되면
CPython이 그 메모리 주소를 새 객체에 재사용하므로, **새 버프가 옛 버프의 상태를
물려받았다.**

증상: 같은 시드인데도 "직전에 어떤 스쿼드를 돌렸는가"에 따라 버프 발동 횟수가 달라졌다
(스쿼드2의 `록 온`·`오토 파이어 레디1`에서 3~7회 편차).

수정: `ActiveBuff.uid` 필드(모듈 전역 `itertools.count()`)를 추가하고
`id(ab)` 사용처를 전부 `ab.uid`로 교체. 주소 재사용 문제 자체가 사라진다.

영향 범위: **딜 수치에는 영향이 없었다** (activate 이벤트 발생 여부만 좌우).
다른 4개 스쿼드는 수정 전후 완전히 동일했다.

> 교훈: 수명이 다른 dict의 키로 `id()`를 쓰지 않는다. 새 코드에서도 마찬가지.
