# 회귀 하네스

계산기를 고친 뒤 **기존 캐릭터가 조용히 틀어졌는지** 잡는 도구.

```bash
python -m context.snapshot                  # 전체 비교
python -m context.snapshot --squad 스쿼드1   # 일부만
python -m context.snapshot --list           # 스쿼드 목록
python -m context.snapshot --update         # baseline 갱신 (유저 확인 후에만)
```

전체 25스쿼드 약 100초. FAIL 시 exit code 1.

---

## 기본 스펙 — `context/spec.py`

총딜 수치를 해석하려면 어떤 스펙으로 돌린 것인지 알아야 한다. 스쿼드 dict는 이름만 주고
나머지는 `context/spec.py`가 채운다. **하네스 전용이 아니다** — `context/sim.py`와
`/report`(`.agent/skills/report/report.py`)가 같은 것을 쓴다. 세 도구의 총딜을 서로
견줄 수 있는 건 기본 스펙이 하나이기 때문이다.

합성은 두 층이다 (뒤가 이긴다, dict는 재귀 병합):

```
spec.DEFAULT_CHAR  →  data/char_defaults.json[이름]  →  호출자 오버라이드
   기본 육성 스펙       캐릭터별 기본 레이어              스쿼드/케이스별 예외
```

### 1층 — 기본 육성 스펙 (`spec.DEFAULT_CHAR`)

| 항목 | 값 |
|---|---|
| 레벨 / 돌파 / 코어 강화 / 친밀도 | 400 / 3 / 0 / 30 |
| 스킬 레벨 | 전부 10 |
| 버스트 리젠 시간 | 2.0s |
| 장비 등급 | 전 부위 T5 |
| 장비 옵션 합산 | **우월코드 대미지 80% · 공격력 20% · 최대 장탄 120%** (나머지 옵션 0) |
| 큐브 | 재장 Lv.15 |
| 콘솔 | 공용 180 / 클래스 100 / 회사 100 |
| 컬렉션 단계 | SR15 |
| 컨트롤 | 없음 — **자동 사격이 디폴트** |

### 2층 — 캐릭터별 기본 레이어 (`data/char_defaults.json`)

니케마다 실전 운용이 다르다. **늘 그렇게 굴리는 캐릭터**의 차이분만 여기 적는다.
1층과 같은 캐릭터는 아예 등록하지 않는다.

| 캐릭터 | 레이어 | 근거 |
|---|---|---|
| 앨리스 | 차지속도 옵션 **8.18%** + 톡톡이(3.6) | 버스트 중 차지속도 100%를 맞추는 게 전제 — `CONTROL.md §앨리스` |
| 아인 | 톡톡이(3.6) | 차지형 톡톡이 대상 |
| 밀크 : 블루밍 바니 | 톡톡이(3.6) + 풀차지 섞기 5.5s + 홀드컨 `charge_hold_after_fb` | 셋이 한 벌이다 — `CONTROL.md §풀차지 섞기`·`§charge_hold:N` |
| 리버렐리오 · 홍련 : 흑영 · 네온 : 비전 아이 | 차지속도 옵션 **8.0%** | 차지형 실전 장비 세팅 |
| 프리바티 · 아니스 : 스파클링 서머 · 헬름 | 최대 장탄 옵션 **0%** | 장탄 옵션을 쓰지 않는 자리 |
| 마스트 : 로망틱 메이드 | 버스트 패턴 — 같은 단계 20초 쿨 동료가 있을 때만, **가장 왼쪽이면 `1,3,5,9,11,14` · 아니면 `3의 배수`** | 아래 §버스트 운용 패턴 |
| 미란다 · 츠바이 · 토브 | 버스트 패턴 **전담** = 매 사이클 (같은 단계에 다른 멤버가 있을 때만) | B1 20초 · 이 셋이 든 덱은 1버를 이쪽이 전담하고 다른 1버는 쓰지 않는다 |
| 프리카 | 버스트 패턴 **첫 사이클만** (민트와 함께일 때만) | 첫 버스트는 프리카, 이후는 전부 민트 |
| 에이다 | 홀드컨 `own_full_burst` lead 0.5 — **미란다와 함께일 때만** | 미란다 `웨이크업! 4`(1발 유지)를 아낀다 — `CONTROL.md §에이다` |
| 미하라 : 본딩 체인 | 엄폐컨 `own_full_burst` — **미란다와 함께일 때만** | 같은 버프를 MG라 엄폐로 아낀다 — `CONTROL.md §미란다 + 미하라` |
| 아인 | (위 톡톡이에 더해) 홀드컨 `own_full_burst` lead 0.5 — **에이다와 함께일 때만** | 에이다와 같은 운용 |
| 아르카나 | 풀버스트 상한 `_max_burst_count` **18** | 사이클이 빨라 180초에 15~16회를 돈다. 아래 §풀버스트 상한 |

#### 풀버스트 상한 — `_max_burst_count`

**시뮬 자체는 상한이 없다** (`timeline` 기본 `None`). 상한을 거는 건 보고서 러너뿐이고
(기본 14회), 사이클이 빠른 스쿼드는 거기 걸려 **조용히 낮게 나온다.** 그래서 필요한 값을
캐릭터 레이어에 등록해 두고 스쿼드에 그 캐릭터가 있으면 러너가 올린다
(`spec.max_burst_floor()` → `report.load_spec`).

`999` 같은 값을 스펙에 박는 것과 다르다 — 상한이 왜 필요한지가 캐릭터에 붙어 있고,
같은 캐릭터를 쓰는 다른 보고서에도 따라간다. **스펙에 `max_burst_count`를 적으면 그 값이
이긴다** (일부러 낮춰 자르는 것도 유효한 비교다).

**`timeline.py`는 이 파일을 읽지 않는다.** `simulate()`는 넘겨받은 캐릭터 dict만 본다 —
기본값이 시뮬 결과를 소리 없이 바꾸면 안 되기 때문이다. 레이어를 얹는 건 언제나 러너 쪽이다.

#### 버스트 운용 패턴

캐릭터마다 "몇 번째 풀버스트에 버스트를 쓰는가"가 정해져 있는 경우가 있다. 카탈로그를
`_burst_patterns`에 이름 붙여 저장하고, 기본으로 쓸 이름을 `burst_pattern`에 적는다.

```jsonc
"마스트 : 로망틱 메이드": {
  "_burst_patterns": { "3의 배수": "every:3", "1,3,5,9,11,14": [1, 3, 5, 9, 11, 14] },
  "burst_pattern": "3의 배수",                                   // 조건이 맞을 때의 기본값
  "_burst_pattern_when": { "same_stage_cd_max": 20 },            // 안 맞으면 패턴 자체가 없다
  "_burst_pattern_rules": [                                      // 먼저 맞는 규칙 하나가 이긴다
    { "when": { "position": 1 }, "use": "1,3,5,9,11,14" }
  ]
}
```

양 끝 값의 뜻 — `"every:1"`은 **매 사이클 등급 0**(그 단계를 전담한다. 미란다·츠바이·토브),
빈 목록 `[]`은 **어느 사이클도 차례가 아니다** = 늘 등급 2다. 후자는 패턴 없음(등급 1)과
다르므로 `_pattern_rank`는 falsy가 아니라 `is None`으로 가른다.

**패턴은 후보에서 빼는 게 아니라 순서를 바꾼다** (`timeline._pattern_rank`).

| 등급 | 누구 | 효과 |
|---|---|---|
| 0 | 패턴이 있고 **이번 사이클이 그 차례** | 패턴 없는 동료보다 **앞선다** |
| 1 | 패턴 없음 | 평소 순서 |
| 2 | 패턴이 있으나 이번 차례가 아님 | 맨 뒤 — 앞사람이 전부 쿨이면 그래도 나간다 |

등급 2가 있어서 단계가 **막히지는 않는다** — 앞사람이 전부 쿨이면 차례가 아니어도 나간다.

**적용 조건 — `_burst_pattern_when`**

"정석"이 조합에 달린 경우가 있다. 마스트 : 로망틱 메이드의 3의 배수는 **20초 쿨 2버와
함께일 때** 성립하는 운용이고, 같은 단계가 40초짜리뿐이면(앵커 : 이노센트 메이드와 둘 등)
격 사이클로 번갈아 쓰는 평소 순서가 맞다. 조건이 안 맞으면 패턴을 **아예 걸지 않는다.**

| 조건 키 | 의미 |
|---|---|
| `same_stage_cd_max: N` | 같은 버스트 단계에 쿨타임 N초 이하인 **다른 멤버가 있을 때만** 적용 (`burst_stage: "A"`는 어느 단계로도 센다) |
| `same_stage_other: true` | 같은 단계에 **다른 멤버가 하나라도 있을 때만.** 자기가 그 단계의 유일한 멤버면 패턴("안 씀")이 무의미하므로 떼어낸다 |
| `with_member: [이름...]` | 목록 중 **하나라도 스쿼드에 있을 때만** (프리카 ← 민트) |
| `position: N` | 스쿼드 배치가 **N번째일 때만** (1 = 가장 왼쪽) |

**어느 패턴이냐 — `_burst_pattern_rules`**

조건은 맞는데 그 안에서 정석이 또 갈릴 때 쓴다. `[{ "when": {...}, "use": "패턴 이름" }, ...]`을
위에서부터 보고 **먼저 맞는 하나**가 `burst_pattern`을 갈아끼운다. 아무것도 안 맞으면
기본값 그대로다. 마스트 : 로망틱 메이드가 유일한 사용처 — 20초 쿨 2버와 함께라는 조건 아래,
가장 왼쪽이면 `1,3,5,9,11,14`, 아니면 `3의 배수`.

조건·규칙은 **레이어 기본값에만** 걸린다. `chars`·보고서 스펙·CLI로 직접 지정한 패턴은 조건을
보지 않는다 — 지정은 언제나 이긴다(값이 우연히 기본값과 같아도 그렇다). 판정은
`spec.resolve_patterns()`가 스쿼드를 조립할 때 하고, **조건에 걸려 떨어진 패턴은
캐릭터 dict에서 빠지므로 이탈 보고에도 실제로 걸린 것만 남는다.**

바꾸는 법: `chars`/보고서 스펙에 `"burst_pattern": "1,3,5,9,11,14"`, 끄려면 `null`
(CLI는 `--burst-pattern "이름:패턴"` / `"이름:없음"`). 등록되지 않은 이름을 주면 즉시 에러다.

`burst_sequence`(사이클별 명시 순서)를 준 config에서는 패턴이 무시된다 — 그쪽이 전부 결정한다.

#### 조합 조건부 컨트롤

컨트롤도 조합에 달릴 수 있다. `_control_rules`에 `[{ "when": {위 조건 키}, "control": {...} }, ...]`을
적으면 **맞는 규칙 전부**가 순서대로 `control`에 병합된다 (패턴은 값이 하나라 먼저 맞는 하나가
이기지만, 컨트롤은 톡톡이+홀드처럼 겹쳐 쓰는 게 정상이다). 판정은 `spec.char_layer(name, members)`가
스쿼드를 조립할 때 하고, 붙은 컨트롤은 이탈 보고에 `(레이어)`로 잡힌다.
의미·수치 근거의 정본은 `CONTROL.md §캐릭터별 기본 컨트롤`.

### 3층 — 호출자 오버라이드

`SQUADS[*]["chars"]`는 **그 스쿼드에서만** 다른 것을 적는 자리다 (예: `레이드_작열짬`의
앨리스 장전컨, `컨트롤_미란다미하라`의 미하라 공격력 30%). 어디서든 그렇게 굴리는 설정이면
`chars`가 아니라 2층에 적는다 — 같은 값을 스쿼드마다 반복하면 갈라진다.
컨트롤을 통째로 끈 대조군이 필요하면 `context/sim.py --auto`를 쓴다.

### 이탈 보고 — 1층이 아니면 언제나 알린다

**2층·3층이 붙은 결과는 그 사실을 함께 낸다.** 수치만 보고 "기본 스펙 결과"로 읽는 게
이 프로젝트에서 가장 조용히 틀리는 경로라서, 사람의 성실성이 아니라 도구가 강제한다.

| 도구 | 어떻게 |
|---|---|
| `context/sim.py` | 스쿼드 줄 바로 아래 이탈 목록 (이탈 없으면 "1층 그대로" 한 줄) |
| `/report` | 탭 상단 **접히지 않는** 경고 배너 |
| `context/snapshot.py` | `meta.spec_deviations`로 baseline에 박힌다 → **딜이 안 움직여도 레이어가 바뀌면 FAIL**. `--list`도 함께 출력 |

**Claude는 이 줄을 유저 답변에도 그대로 옮긴다.** 시뮬 결과를 보고할 때 1층이 아니었으면
어떤 레이어·오버라이드가 붙었는지 먼저 적는다. 구현은 `spec.format_deviations()` /
`spec.squad_deviations()`.

즉 **하네스 총딜은 실전 기대딜이 아니다.** 스펙이 고정된 비교용 수치일 뿐이다.

## 이 도구가 하는 일과 하지 않는 일

**한다** — 변화 감지. "무엇이 이전과 달라졌는가"를 캐릭터·효과 단위로 짚는다.

**하지 않는다** — 정확성 검증. baseline을 찍는 순간 그 시점 코드의 **기존 버그도 "정상"으로 고정**된다.
정확성은 `context/scenarios/<이름>.md`의 검증 체크리스트가 담당한다.

즉 하네스가 PASS라고 해서 계산이 맞다는 뜻이 아니다. "내가 방금 고친 것 때문에
다른 게 바뀌지는 않았다"는 뜻이다.

---

## 왜 결정론적인가

`simulate(..., seed=N)`을 주면 크리 판정·코어히트·`prob:N` 조건·`allies_random`이
모두 재현되어 결과가 완전히 같아진다. 프로세스가 달라도, `PYTHONHASHSEED`가 달라도 같다.

그래서 **오차 범위가 없다. 완전 일치해야 PASS다.**

> 참고 — `simulate()`의 `seed` 기본값은 `None`(시드 미고정)이다. 기대딜은 여러 회 평균이
> 맞으므로 시드를 안 주고 돌리면 매번 다른 값이 나온다(`context/sim.py`의 기본 동작).
> 시드는 하네스·`context/sim.py --seed`·보고서(고정 시드셋 `[1..runs]`)가 명시적으로 넘긴다.

## 스냅샷 4층 구조 — diff 읽는 법

절대 시각은 저장하지 않는다. 발사 타이밍이 1프레임(0.0167s) 밀리는 건 노이즈지만,
**"버프가 적용된 다음에 대미지가 계산되는가" 하는 순서는 신호**이기 때문이다.

### L1 수치 — 무엇이 얼마나
캐릭터별 총딜, 스킬별 딜·히트수, `hit_tag` 분포, 크리 수, 풀버스트 횟수.

```
[L1 수치]
스쿼드 총딜  1,862,282,550 → 1,863,145,587  (+863,037, +0.05%)
[라피 : 레드 후드] 스킬 <부착형 유탄 4>  딜 225,995,644 → 226,031,557  히트 106 → 106
```
→ **L1만 움직였다면** 순수한 계수·수치 변경이다. 발동 타이밍은 그대로.

### L2 발동 횟수 — 몇 번 걸렸나
버프/인스턴트 이름별 발동 횟수와 대상 집합.

```
[L2 발동 횟수]
! 버프 [붉은 두건] 발동 12 → 9회
+ 버프 [○○] 신규 발동 4회 → ['미하라']
- 버프 [××] 발동 사라짐 (기존 30회)
```
→ **가장 먼저 볼 층.** 버프가 안 걸리게 된 회귀는 여기서 바로 드러난다.
딜이 상쇄되어 L1이 조용해도 L2는 반응한다.

### L3 순서 — 무엇 다음에 무엇이
풀버스트 진입을 경계로 사이클을 나누고, 각 사이클 안의 이벤트를 **시각 없이 순서열로** 기록.
히트는 이벤트 사이 구간의 집계로 압축한다.

```
[L3 순서]
── 사이클 1 순서 변화 ──
   B+ 릴렉스 → 크라운
  -HITS 라피 : 레드 후드:1 crit:0 core:0
  +HITS 라피 : 레드 후드:3 crit:0 core:0
   B- 터진 거품 2 → __enemy__
```
표기: `B+` 버프 활성 / `B-` 버프 만료 / `I` 인스턴트 / `BURST` 버스트 이벤트 / `HITS` 구간 히트 집계.

→ **버프와 히트의 상대 순서**가 바뀌면 여기서 잡힌다. 1프레임 밀림은 diff를 만들지 않지만,
버프가 히트보다 뒤로 밀리면 즉시 드러난다.

### L4 위상 — 정수 지표
사이클 간격(0.05초 정밀도)과 "버프 발동 → 대상의 다음 히트까지 프레임 수" 분포.

```
[L4 위상]
사이클 간격  [12.55, 12.55, ...] → [12.55, 17.30, ...]
버프 [○○] 발동→다음히트  3프레임 11→8, 4프레임 22→25
```
→ 사이클 간격이 12.5초에서 크게 벗어나면 버스트 사이클이 깨진 것이다.

## baseline 갱신 규칙

`context/baseline/*.json`은 **자동 생성물이다. 손으로 편집하지 않는다.**

FAIL이 났을 때:

1. diff를 **그대로 유저에게 보고**한다. 재시도하지 않는다.
2. 유저가 "그 변화는 의도한 것"이라고 확인해준 뒤에만 `--update`.
3. 의도치 않은 변화면 회귀다 — 원인을 찾을 때까지 갱신하지 않는다.

스쿼드를 추가하려면 `context/snapshot.py`의 `SQUADS`에 항목을 넣고
`--update --squad <이름>`으로 baseline을 만든다.

> **baseline 세대 경계 — 2026-08-07 기본 스펙 전환.** 그날 25스쿼드 baseline을 전부
> 새로 찍었다(커밋 `c0a0b0a`). 종전에는 장비 옵션이 하나도 없는 스펙으로 돌렸으므로
> **그 이전 총딜·델타는 지금 값과 직접 비교되지 않는다.** 옛 문서·커밋 메시지에서
> 총딜 수치를 인용할 때는 이 경계를 먼저 본다.

과거 baseline 갱신 내역은 이 문서가 아니라 **git log**가 정본이다
(`git log --oneline -- context/baseline`). 변경 사유·수치 근거는 해당 커밋 메시지와
`context/scenarios/*.md`에 있다.

### 미커버

파싱은 됐지만 아직 어느 스쿼드에도 없는 캐릭터다. 새 스쿼드를 짤 때 우선 후보다.

마르차나 : 마린 스터디 · 신데렐라 : 크리스탈 웨이브 · 라플라스 : 얼티밋 히어로 · 트리나 ·
맥스웰 : 오디너리 미케닉 · 플로라 · 슈가 · 팬텀 · 로산나 · 아크레인저 블랙 · 레이 (가칭)

### 적 속성 (`enemy` 키)

스쿼드 dict의 `enemy`는 `simulate(enemy=...)`로 그대로 넘어간다 (`DEFAULT_ENEMY` 오버라이드).
**키가 없으면 무속성 적**이라 `is_element_match`(DealForm ⑦)가 영구 거짓이다.

작열 약점 솔로레이드는 `{"code": "풍압"}`이다 — 적 코드에 **우월한** 캐릭터가 유리를 받으므로
(작열 → 풍압, `damage._CODE_ADVANTAGE`), "작열 약점"은 적 코드가 풍압이라는 뜻이다.
이때 작열 캐릭터의 딜은 ×1.2909가 된다 (⑦ 기본 +10% + 기본 스펙의 공통 큐브 Lv15 우월코드 대미지 19.09%).

현재 이 키를 쓰는 스쿼드: `스쿼드3` · `레이드_브리드디젤` · `레이드_라피앨리스` · `레이드_작열짬` ·
`컨트롤_미란다미하라` · `컨트롤_에이다미하라`. 나머지는 전부 무속성이며, 두 경우를 모두 남겨 두는 게 의도다.

### 컨트롤 스쿼드

컨트롤은 **캐릭터별 기본 레이어가 있는 니케를 뺀 나머지가 전부 자동**이다(§2층 표).
그 니케가 없는 스쿼드에는 정책 코드가 아예 들어오지 않으므로, 정책은 따로 스쿼드를 둬서 덮는다.

`chars` 키로 캐릭터별 설정을 덮어쓸 수 있다 — 그 스쿼드에서만 컨트롤을 켜거나, 정책이
의미를 갖는 데 필요한 장비 옵션을 주는 용도다. **기본 스펙·레이어로 표현되는 것은 쓰지 않는다.**
엄폐컨·홀드컨은 2026-08-07에 조건부 레이어로 내려갔으므로 `컨트롤_*` 스쿼드의 `chars`에
더는 적지 않는다 — 미란다가 함께 있는 것만으로 켜진다.

| 스쿼드 | 커버하는 정책 |
|--------|---------------|
| `컨트롤_미란다미하라` | `cover.policy: own_full_burst` (버스트 엄폐컨 — 레이어) |
| `컨트롤_에이다미하라` | `hold.policy: own_full_burst` (홀드컨) + 엄폐컨 병행 (둘 다 레이어) |
| `레이드_미하라에이다` | 위와 같은 조합·같은 컨트롤, 우월 코드만 없음 |
| `레이드_라피앨리스` | `tap_fire`(앨리스 톡톡이 — 레이어) + `reload.policy: before_fb_end`(라피 장전컨 A) 병행 |
| `레이드_작열짬` | `tap_fire`(레이어) + `reload.policy: into_fb`(장전컨 B) — 한 캐릭터에 둘 |

설정값의 의미·손익 판단 기준은 `CONTROL.md`가 정본이다. `reload.margin`처럼 조합마다
다시 재야 하는 값은 `snapshot.py`의 해당 스쿼드 주석에 근거를 적어 둔다.

`레이드_*`인데 컨트롤도 함께 덮는 스쿼드가 있다 — 실전 조합이 곧 컨트롤 조합이라 따로 지그를
만들지 않았다. **컨트롤 4종(톡톡이·장전컨 A/B·엄폐·홀드)이 위 스쿼드로 전부 덮인다.**

> **동시 컨트롤 1명 제약은 검사하지 않는다** (`CONTROL.md §미구현`). `레이드_라피앨리스`는
> 실전에서 "라피 장전컨을 먼저 치고 남은 시간에 앨리스 톡톡이"인데, 계산기는 둘을 동시에
> 굴린다 — 라피를 조작하는 짧은 구간의 앨리스 톡톡이 손실만큼 **낙관적인 상한**이다.

실전 조합이 없는 캐릭터(리타처럼)는 `GAMEPLAY.md §스쿼드 구성 §표준 테스트 스쿼드`의
템플릿에 `TARGET`만 갈아끼워 만든다. 버스트 단계·쿨다운별 템플릿이 거기 있다.

`레이드_*`의 조연은 임의 지그가 아니라 **실제 상위 조합 그대로**다.
따라서 실전에서 실제로 맞물리는 버프 상호작용까지 스냅샷에 들어온다.
대신 조합을 바꾸면 baseline이 통째로 흔들리므로, **커버 대상만 보고 조연을 갈아끼우지 않는다.**

### 스쿼드를 새로 추가할 때

> **시작 전 필수** — `context/GAMEPLAY.md`의 `## 스쿼드 구성` 절을 읽는다.
> (§유효한 스쿼드의 조건 / §버스트 쿨타임 감소 / §**버스트 사용 순서와 배치** / §더미 캐릭터)

특히 다음 두 가지는 이 하네스를 만들면서 실제로 밟은 함정이다.

- **멤버 순서 = 버스트 사용 순서다.** 관찰 대상은 반드시 **자기 단계 안에서 맨 앞**에 둔다.
  뒤로 밀리면 같은 단계의 앞사람에게 선점당해 **버스트를 한 번도 못 쓴 채** 스냅샷이 찍힌다.
  초기 배치에서 소다·델타·헬름:아쿠아마린·나가·벨벳·프리카 6명이 이 상태였다.
- **레드 후드(`burst_stage: "A"`)의 단계를 고정하지 않는다.** 고정하면 라피 : 레드 후드의
  `no_burst1_ally` 조건이 깨져 라피의 1버 전환이 막힌다. 배치 순서로만 조정한다.

그 밖에:

- `test_B3`를 한 스쿼드에 두 번 넣지 않는다 (`burst_cooldown` 소급 보정 중복).
  B3 두 자리가 필요하면 한쪽은 `스노우 화이트 : 헤비암즈`.
- 버스트를 안 쓰는 캐릭터는 `config={"no_burst_char": "이름"}`. 한 명만 지정할 수 있다.
- **특정 캐릭터를 N사이클마다만 버스트**시키려면 `config={"burst_sequence": [...]}`
  (`레이드_브리드디젤`의 마스트 : 로망틱 메이드가 이 경우 — 3의 배수 사이클에만 버스트).
  엔트리마다 **1·2·3단계를 전부** 적는다. 빠진 단계는 후보 0명이 되어 영구 블록된다
  (`_next_action_t = inf`). 개수는 사이클 수(180초 ÷ 사이클 간격)보다 넉넉히 잡고,
  모자라면 그 뒤로는 자동 순서(`burst_order`)로 폴백한다.
- 버스트 단계·쿨다운은 `data/parsed_nikke.json`의 `burst_stage` / `burst_cooldown`.
