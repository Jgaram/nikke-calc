# 회귀 하네스

계산기를 고친 뒤 **기존 캐릭터가 조용히 틀어졌는지** 잡는 도구.

```bash
python -m context.snapshot                  # 전체 비교
python -m context.snapshot --squad 스쿼드1   # 일부만
python -m context.snapshot --list           # 스쿼드 목록
python -m context.snapshot --update         # baseline 갱신 (유저 확인 후에만)
```

전체 5스쿼드 약 20초. FAIL 시 exit code 1.

---

## 이 도구가 하는 일과 하지 않는 일

**한다** — 변화 감지. "무엇이 이전과 달라졌는가"를 캐릭터·효과 단위로 짚는다.

**하지 않는다** — 정확성 검증. baseline을 찍는 순간 그 시점 코드의 **기존 버그도 "정상"으로 고정**된다.
정확성은 `context/scenarios/<이름>.md`의 검증 체크리스트가 담당한다.

즉 하네스가 PASS라고 해서 계산이 맞다는 뜻이 아니다. "내가 방금 고친 것 때문에
다른 게 바뀌지는 않았다"는 뜻이다.

---

## 왜 결정론적인가

`simulate(..., seed=N)`을 주면 크리 판정·코어히트·`prob:N` 조건·`allies_random`이
모두 재현되어 결과가 완전히 같아진다. 프로세스가 달라도, `PYTHONHASHSEED`가 달라도 같다.

그래서 **오차 범위가 없다. 완전 일치해야 PASS다.**

> 참고 — `simulate()`의 `seed` 기본값은 `None`(시드 미고정)이다.
> UI의 기대딜은 여러 회 평균이 맞으므로 앱은 지금도 매번 다른 값을 낸다.
> 시드는 하네스와 `context/sim.py`만 명시적으로 넘긴다.

## 스냅샷 4층 구조 — diff 읽는 법

절대 시각은 저장하지 않는다. 발사 타이밍이 1프레임(0.0167s) 밀리는 건 노이즈지만,
**"버프가 적용된 다음에 대미지가 계산되는가" 하는 순서는 신호**이기 때문이다.

### L1 수치 — 무엇이 얼마나
캐릭터별 총딜, 스킬별 딜·히트수, `hit_tag` 분포, 크리 수, 풀버스트 횟수.

```
[L1 수치]
스쿼드 총딜  1,862,282,550 → 1,863,145,587  (+863,037, +0.05%)
[라피 : 레드 후드] 스킬 <부착형 유탄 4>  딜 225,995,644 → 226,031,557  히트 106 → 106
```
→ **L1만 움직였다면** 순수한 계수·수치 변경이다. 발동 타이밍은 그대로.

### L2 발동 횟수 — 몇 번 걸렸나
버프/인스턴트 이름별 발동 횟수와 대상 집합.

```
[L2 발동 횟수]
! 버프 [붉은 두건] 발동 12 → 9회
+ 버프 [○○] 신규 발동 4회 → ['미하라']
- 버프 [××] 발동 사라짐 (기존 30회)
```
→ **가장 먼저 볼 층.** 버프가 안 걸리게 된 회귀는 여기서 바로 드러난다.
딜이 상쇄되어 L1이 조용해도 L2는 반응한다.

### L3 순서 — 무엇 다음에 무엇이
풀버스트 진입을 경계로 사이클을 나누고, 각 사이클 안의 이벤트를 **시각 없이 순서열로** 기록.
히트는 이벤트 사이 구간의 집계로 압축한다.

```
[L3 순서]
── 사이클 1 순서 변화 ──
   B+ 릴렉스 → 크라운
  -HITS 라피 : 레드 후드:1 crit:0 core:0
  +HITS 라피 : 레드 후드:3 crit:0 core:0
   B- 터진 거품 2 → __enemy__
```
표기: `B+` 버프 활성 / `B-` 버프 만료 / `I` 인스턴트 / `BURST` 버스트 이벤트 / `HITS` 구간 히트 집계.

→ **버프와 히트의 상대 순서**가 바뀌면 여기서 잡힌다. 1프레임 밀림은 diff를 만들지 않지만,
버프가 히트보다 뒤로 밀리면 즉시 드러난다.

### L4 위상 — 정수 지표
사이클 간격(0.05초 정밀도)과 "버프 발동 → 대상의 다음 히트까지 프레임 수" 분포.

```
[L4 위상]
사이클 간격  [12.55, 12.55, ...] → [12.55, 17.30, ...]
버프 [○○] 발동→다음히트  3프레임 11→8, 4프레임 22→25
```
→ 사이클 간격이 12.5초에서 크게 벗어나면 버스트 사이클이 깨진 것이다.

## baseline 갱신 규칙

`context/baseline/*.json`은 **자동 생성물이다. 손으로 편집하지 않는다.**

FAIL이 났을 때:

1. diff를 **그대로 유저에게 보고**한다. 재시도하지 않는다.
2. 유저가 "그 변화는 의도한 것"이라고 확인해준 뒤에만 `--update`.
3. 의도치 않은 변화면 회귀다 — 원인을 찾을 때까지 갱신하지 않는다.

스쿼드를 추가하려면 `context/snapshot.py`의 `SQUADS`에 항목을 넣고
`--update --squad <이름>`으로 baseline을 만든다.

## 남은 작업 — 커버리지 확대

현재 **파싱된 53명 중 23명(43%)만** 커버한다. 나머지 31명은 계산기를 고쳐도 무방비다.

> **시작 전 필수** — `context/GAMEPLAY.md`의 `## 스쿼드 구성` 절 **전체**를 읽는다.
> (§버스트 쿨타임 현황 / §유효한 스쿼드의 조건 / §버스트 쿨타임 감소 / §더미 캐릭터 / §표준 테스트 스쿼드)
> 스쿼드 편성 규칙이 전부 거기 있다.

`GAMEPLAY.md §표준 테스트 스쿼드`의 템플릿이 대상의 버스트 단계·쿨다운에
그대로 대응하므로, 아래 그룹별로 `TARGET`만 갈아끼우면 스쿼드를 기계적으로 만들 수 있다.
(`test_B1/B2/B3`은 스킬 없는 더미 캐릭터 — 버프·딜 영향 없이 버스트 사이클만 채운다)

### 반드시 알아야 할 규칙 (GAMEPLAY.md 요약 — 링크를 못 타더라도 이것만은)

- **B3는 쿨 최소 40초라 한 사이클에 2명이 필요하다.** B1·B2는 20초면 1명으로 족하다.
  전형적 구성은 `B1×1 + B2×1 + B3×2 + 버스트 미사용×1`.
- **`test_B3`를 한 스쿼드에 두 번 넣지 않는다.** `burst_cooldown` 소급 보정이 중복 계산되어
  쿨타임이 잘못 단축된다. B3 슬롯 두 자리가 필요하면 한쪽은 `스노우 화이트 : 헤비암즈`를 쓴다.
- **B1 슬롯 대용은 `리틀 머메이드`(쿨 20초).** `아니스 : 스타`는 B1이지만 팀에 다른 B1이 있으면
  B1 재진입이 발동해 사이클이 복잡해지므로 대용으로 쓰지 않는다.
- **버스트를 안 쓰는 캐릭터는 `config={"no_burst_char": "이름"}`으로 지정**한다.
- 대상의 버스트 단계·쿨다운은 `data/parsed_nikke.json`의 `burst_stage` / `burst_cooldown`으로 확인.

### 시너지는 고려하지 않는다

이 스쿼드들은 실전 최적 조합이 아니라 **대상 캐릭터의 동작을 안정적으로 관찰하기 위한 고정 지그**다.
딜 시너지를 노려 조연을 바꾸면 baseline이 흔들리고 diff의 원인 추적만 어려워진다.
조연은 템플릿 그대로 두고 `TARGET`만 교체한다.

### B3 / 40s — 16명
`[리틀 머메이드, 크라운, TARGET, test_B3]`

네온 : 비전 아이, 디젤 : 윈터 스위츠, 레이븐, 루드밀라 : 윈터 오너, 메이든 : 아이스 로즈,
미하라 : 본딩 체인, 브래디, 소다 : 트윙클링 바니, 스노우 화이트, 아니스 : 스파클링 서머,
아스카 : WILLE, 앨리스, 에이다, 이브, 일레그 : 붐 앤 쇼크, 퀀시 : 이스케이프 퀸

### B2 / 20s — 7명
`[리틀 머메이드, TARGET, test_B3, 스노우 화이트 : 헤비암즈]`

그레이브, 나가, 민트, 벨벳, 브리드 : 사일런트 트랙, 에이드 : 에이전트 바니, 헬름 : 아쿠아마린

### B1 / 20s — 5명
`[TARGET, 크라운, test_B3, 스노우 화이트 : 헤비암즈]`

D : 킬러 와이프, 루주, 리타, 미란다, 볼륨

### B2 / 40s — 2명
`[리틀 머메이드, TARGET, 크라운, test_B3, 스노우 화이트 : 헤비암즈]`

델타 : 닌자 시프, 프리카

### 예외 — 1명
**레드 후드** — `burst_stage: "A"`(임의 단계)라 템플릿이 없다. 유저 판단 필요.

### 편성 시 주의

- 한 스쿼드에 여러 명을 넣어 스쿼드 수를 줄일 수 있지만, **버프가 서로 섞이면
  diff의 원인 추적이 어려워진다.** 대상 1명 + 고정 조연 구성을 기본으로 한다.
- 편성 후 반드시 버스트 사이클 간격을 확인한다 (`--view burst` 또는 L4 `cycle_gaps`).
  **12.5초에서 5초 이상 벗어나면** 스쿼드 구성이 잘못된 것이다 — baseline을 찍지 말고 중단.
- 스쿼드가 늘면 baseline 용량도 는다 (현재 5스쿼드 1.3MB). 12스쿼드면 약 3MB.

## 이력

### 2026-07-21 — 하네스 도입

- `context/regression_test.py`(총딜 ±3σ, 30회 재측정 방식) 대체.
  이관 시점에 시드 고정 총딜이 기존 5스쿼드 평균 대비 전부 **1σ 이내**임을 확인했다
  (0.15σ ~ 0.98σ). 즉 기존 기준과 모순되지 않는다.
- 기존 방식이 놓치던 범위: 스쿼드1 기준 tol이 ±29,306,951이었으므로
  **0.05%(약 86만) 규모 변화는 검출 불가능**했다. 하네스는 이를 L1에서 잡는다.

### 2026-07-21 — 비결정성 버그 수정 (하네스가 발견)

`BuffManager._cond_passive_prev`가 `id(ActiveBuff)`를 키로 쓰면서, 버프 만료 시
항목을 정리하지 않았다 (`reset()`에서만 `clear()`). 만료된 ActiveBuff가 GC되면
CPython이 그 메모리 주소를 새 객체에 재사용하므로, **새 버프가 옛 버프의 상태를
물려받았다.**

증상: 같은 시드인데도 "직전에 어떤 스쿼드를 돌렸는가"에 따라 버프 발동 횟수가 달라졌다
(스쿼드2의 `록 온`·`오토 파이어 레디1`에서 3~7회 편차).

수정: `ActiveBuff.uid` 필드(모듈 전역 `itertools.count()`)를 추가하고
`id(ab)` 사용처를 전부 `ab.uid`로 교체. 주소 재사용 문제 자체가 사라진다.

영향 범위: **딜 수치에는 영향이 없었다** (activate 이벤트 발생 여부만 좌우).
다른 4개 스쿼드는 수정 전후 완전히 동일했다.

> 교훈: 수명이 다른 dict의 키로 `id()`를 쓰지 않는다. 새 코드에서도 마찬가지.
